Innovating Beyond nom

nom treats the DAG as a tree, hardcodes 4 states, and locks colors to a global var. go-output now has the full DAG. Here are 13 concrete ways to use that data — and to make the status/color system open, themeable, and category-aware.

00The Thesis

nom's limitation is intentional: it was built for Nix, where the build graph is massive (thousands of derivations) and the user only cares about "what's happening right now." Showing topology would be noise. So nom deduplicates, picks the deepest parent, and shows a tree.

go-output's opportunity is different: it's a general-purpose library, not tied to Nix. Its consumers (BuildFlow, CI pipelines, deployment tools) have smaller, denser DAGs where understanding the topology is the difference between "why is this slow?" and "oh, Test is blocked because Lint hasn't finished." nom can't answer that question. We can.

The DAG topology model (node.Deps, computeDepths()) is already in place. Everything below uses that data. The question isn't whether to innovate — it's which innovations deliver the most value for the least complexity.

01Layered / Topological Display Mode

Novel Tier 1 Medium Effort

The Idea

Instead of a tree, group nodes by their dependency depth (topological sort waves). Each layer is a row of independent, parallel-safe activities. The position encodes the dependency — no annotation needed.

Layer 0 │ ◈ Build ────────┼────────────────────────────────── Layer 1 │ ⏵ Compile 2.3s ✔ Lint 1.1s ────────┼────────────────────────────────── Layer 2 │ ○ Test (blocked: waiting for Compile) ────────┼────────────────────────────────── Layer 3 │ ○ Deploy

Test appears in Layer 2 because it depends on both Compile and Lint — that's visible from the position. In tree mode, you'd need an annotation to know Test depends on both. In layered mode, the layer number IS the dependency information.

Why nom can't do this

nom doesn't expose dependency depth as a concept. Its tree is built from parent-child links, not topological layers. go-output's computeDepths() already computes the exact data needed (longest path from root per node).

Implementation

  • RenderLayeredWithSnapshots() on DependencyTree — groups nodes by node.Depth
  • Within each layer, sort by priority (same childPriority logic)
  • Layer separator lines (────│────) between groups
  • WithRenderMode(RenderModeLayered) subscriber option
  • InlineRenderer and TUI both consume via the same entry interface

Challenges

  • Wide layers: Layer 1 might have 8 parallel tasks. Need wrapping or column layout.
  • Height pressure: each layer takes 2+ rows (header + nodes). A 10-layer DAG needs 20+ rows.
  • TUI scroll: visibleEntries[treeLine] mapping needs rework for layer-aware entries.
Verdict: Build this first. It's the flagship feature — the one thing no other terminal progress tool does.

02Critical Path Highlighting

Novel Tier 1 Low Effort

The Idea

With the real DAG, we can compute the critical path — the longest dependency chain from root to the deepest leaf. This is the chain that determines total build time. Highlight it so users see their bottleneck immediately.

◈ Build ├── ✔ Fetch 0.2s ├── ⏵ Compile 12.4s ◆ critical │ └── ⏵ Link 8.1s ◆ critical │ └── ○ Package ◆ critical └── ✔ Lint 1.1s

The critical path (Compile → Link → Package) gets a subtle ◆ critical marker. The user instantly sees: "if I want to speed up the build, I need to optimize Compile or Link. Lint is irrelevant."

Why this matters

nom shows you what's running. It can't tell you what matters. In a 20-step pipeline with 3 parallel branches, only one branch is the bottleneck. Critical-path highlighting surfaces that without the user having to trace dependencies manually.

Implementation

  • dt.CriticalPath() []ActivityID — longest path through the DAG by estimated time
  • Uses timing cache data (snap.EstimatedTime) + elapsed for running nodes
  • Renderer adds ◆ marker (or bold styling) to nodes on the critical path
  • Summary bar shows "critical path: ~4m 30s"
Verdict: Low effort, high impact. The DAG + timing cache already have the data. Just compute + render.

03Blockage / Waiting View

Novel Tier 1 Medium Effort

The Idea

When a node is pending (blocked), show why it's blocked and how close its blockers are to completing. This is the "why isn't this starting?" question that nom completely ignores.

◈ Build ├── ⏵ Compile 45% (4.2s / ~9.3s) ├── ✔ Lint 1.1s └── ○ Test └ blocked: Compile (45%), Package (not started)

Test isn't just "pending" — it's specifically blocked on Compile (45% done) and Package (hasn't started). The user can see exactly what needs to happen before Test can run.

Why nom can't do this

nom's deduplication means a pending derivation may appear under a parent that isn't its real blocker. With the full DAG (node.Deps), we can check every dependency's status and report which ones are still incomplete.

Implementation

  • For each pending node, iterate node.Deps and check each dep's snapshot status
  • If any dep is not completed/failed, show the blockage reason
  • For running deps, show progress percentage or elapsed/estimated
  • For pending deps, show "not started"
  • Render as a dim sub-line beneath the pending node (same pattern as Progress/ExtraDeps)
Verdict: Medium effort, very high UX impact. This answers the #1 question users have during a build: "why isn't this step running yet?"

04Parallelism Meter

Novel Tier 2 Low Effort

The Idea

Show how many activities are running in parallel right now vs. how many could be running. This tells the user whether their pipeline is CPU-bound (everything is running) or dependency-bound (waiting for a bottleneck).

╭───────────────────────────────────╮ │ ⏵3 ○5 ✔2 parallel: 3/4 possible │ ╰───────────────────────────────────╯

"3/4 possible" means 3 tasks are running but 4 could be — one slot is idle because the next task is blocked. This is a single-line addition to the summary bar.

Implementation

  • Count running activities = currently parallel
  • Count pending activities whose deps are ALL complete = could-be-parallel
  • running + could-be-parallel = max possible parallelism at this moment

05Critical Path ETA

Novel Tier 2 Medium Effort

The Idea

nom's ETA sums all estimated times. This is wrong for parallel DAGs — 5 parallel 10-second tasks take 10 seconds, not 50. go-output can compute the true remaining time by finding the longest path through the remaining work.

╭─────────────────────────────────────────╮ │ ⏵2 ○4 ✔3 ~2m 15s left (critical path) │ ╰─────────────────────────────────────────╯

Instead of summing all remaining estimates, walk the DAG from each root, taking the max at each branch point. The result is the true minimum remaining time given perfect parallelism.

Implementation

  • EstimatedTotalRemaining() already exists but sums all activities
  • Add EstimatedCriticalPathRemaining() that walks the DAG taking max at branches
  • For running nodes: max(0, estimated - elapsed)
  • For pending nodes: full estimated
  • Summary bar shows the critical-path estimate instead of (or alongside) the sum
Note: The existing EstimatedTotalRemaining in nom_subscriber.go already has per-activity remaining logic. The DAG version adds the max-at-branch computation.

06Convergence Markers (Fan-in Detection)

Novel Tier 2 Low Effort

The Idea

Detect "convergence points" — nodes with 2+ dependencies where parallel branches merge back together. These are the places where one slow branch blocks everything. Mark them so the user knows "this is where the pipeline narrows."

◈ Build ├── ✔ Fetch ├── ⏵ Compile ─────────────┐ ├── ✔ Lint ──────────────────┐ │ └── ○ Test ◆ converge (2 deps) ← waits for both

The ◆ converge marker appears on any node with len(node.Deps) > 1. It tells the user: "this node is a bottleneck point — it can't start until ALL its dependencies finish."

Implementation

  • Already have ExtraDeps() which returns deps beyond the display parent
  • If len(node.Deps) > 1, render ◆ marker
  • Works in both tree mode and layered mode

07Compact DAG Summary Line

Novel Tier 2 Low Effort

The Idea

A single-line topology summary at the top of the display, giving at-a-glance DAG shape understanding:

DAG: 7 nodes, 9 edges, 4 layers, critical path: ~4m 30s

Or in a more visual form:

DAG ▸ 4 layers ▸ 7 nodes ▸ widest: 3 parallel ▸ critical: Compile→Link→Package

Implementation

  • len(dt.nodes) = node count
  • Count edges: sum(len(node.Deps))
  • max(node.Depth) + 1 = layer count
  • Max nodes at any depth = widest layer
  • Critical path = longest estimated-time chain (from idea #2)

08Smart Layer Filtering

Novel Tier 3 Medium Effort

The Idea

For large DAGs (50+ nodes), show only the layers with active work. Completed layers collapse to a summary; pending layers that aren't next are hidden.

✔ Layer 0: Build (done) ✔ Layer 1: Fetch, Unpack (done) ⏵ Layer 2: Compile, Lint, Type-Check ├── ⏵ Compile 8.2s ├── ⏵ Lint 3.1s └── ✔ Type-Check 0.8s ⋯ 2 more layers (Test, Deploy)

This combines the layered view with the existing height-pressure collapse, but collapsed at the layer level instead of the node level. "Layer 0 and 1 are done, here's the detail for the active layer, and there are 2 more layers after this."

09Critical-Path-Aware Rendering Priority

Novel Tier 3 Medium Effort

The Idea

When height pressure forces the renderer to drop nodes, keep critical-path nodes visible and deprioritize nodes that aren't on any critical path. nom's priority sort is by interest (failed > running > completed). We add a second dimension: critical-path nodes get a priority boost.

In a 30-node DAG with height limit 10, this means the user always sees the bottleneck chain, not random leaf nodes that happen to sort first.

Implementation

  • Compute critical path set (idea #2)
  • In sortKeyForNode() (tree_priority.go), add a onCriticalPath bool field
  • Critical-path nodes sort before non-critical nodes at the same interest level

10Interactive DAG View (TUI)

Novel Tier 3 High Effort

The Idea

In the TUI, let the user toggle between rendering modes with a keypress:

  • T — Tree mode (current default, Option A)
  • L — Layered mode (idea #1)
  • C — Critical path view (shows only the critical chain)
  • D — DOT export (writes the DAG as a .dot file)

The TUI already has DisplayMode (NOM vs Universal). Adding a render-mode toggle within NOM mode gives the user agency over how they consume the DAG.

Why this is Tier 3

Each view mode needs its own scroll logic, entry type, and rendering path. The TUI already has two modes (NOM + Universal) with separate scroll implementations. Adding layered mode means a third. This is worth doing but should come after the core layered renderer is proven in the InlineRenderer first.

11Open Status Registry (User-Defined States)

Novel Tier 1 Medium Effort

The Problem

ActivityStatus is a closed iota enum with exactly 4 values (activity_status.go:18). A CI pipeline that wants Skipped, Cached, Unstable, Warning, or Cancelled has nowhere to put them. They collapse into one of the four, losing semantic information. Every consumer of this library for non-Nix use cases hits this wall.

The Idea

Replace the closed enum with a registration-based system. Core states are pre-registered at init() time; users add their own at runtime. The registry maps int → StatusDef{Name, Symbol, Color, Interest, Shape}. 

// Pre-registered — backward compatible (IDs 0-3)
var ActivityStatusPending   = RegisterStatus("pending",   SymbolPending,   Colors.Pending)
var ActivityStatusRunning   = RegisterStatus("running",   SymbolRunning,   Colors.Running)

// User extends at runtime — no library change needed
var ActivityStatusSkipped   = RegisterStatus("skipped",   "⊘", lipgloss.Color("8"))
var ActivityStatusCached    = RegisterStatus("cached",    "▤", lipgloss.Color("14"))
var ActivityStatusWarning   = RegisterStatus("warning",   "▲", lipgloss.Color("11"))
var ActivityStatusCancelled = RegisterStatus("cancelled", "✕", lipgloss.Color("9"))

Rendering looks up the def by status ID at render time. Interest() (sort priority) becomes user-configurable — a "warning" state can sort between running and failed.

◈ CI Pipeline ├── ⊘ Skipped Step ← user-defined "skipped" ├── ▤ Cached Build 0.0s ← user-defined "cached" (from cache) ├── ⏵ Test Suite 12.3s ← standard running ├── ▲ Lint (warnings) 2.1s ← user-defined "warning" └── ✔ Deploy 3.4s ← standard completed

Key Design Decisions

  • ActivityStatus stays int — backward compatible, comparable, usable as map key
  • Core constants keep working (they're just pre-registered IDs 0-3)
  • AllActivityStatuses becomes dynamic (returns registry entries)
  • ParseActivityStatus / IsValid check the registry, not a hardcoded list
  • ActivitySnapshot carries the ActivityStatus int; renderers resolve via registry
  • Thread-safe via sync.RWMutex on the registry

Why nom can't do this

nom's states are baked into Haskell's type system — adding a new state means modifying the library and recompiling. go-output's runtime registry lets consumers extend without forking.

Verdict: Highest user impact of all 13 ideas. Unblocks entire use cases (CI with skipped/cached/warning states). The registration API is small; the hard part is auditing every switch on ActivityStatus to use the registry instead of hardcoded cases.

12Theme System (Configurable Colors + Symbols)

Novel Tier 1 Medium Effort

The Problem

Colors (symbols.go:69) is a hardcoded package-level global with no override mechanism. No WithTheme(), no SetColors(), no config file. The TUI delegates to this global (tui/colors.go:37-40), so it's equally locked. If you want blue for running instead of yellow, you fork the library.

The Idea

Make the Colors global injectable via subscriber options, with preset themes and terminal-background auto-detection. 

// Option 1: Preset themes
sub := nom.NewNOMStyleSubscriber(nom.WithTheme(nom.ThemeDracula))

// Option 2: Custom theme
sub := nom.NewNOMStyleSubscriber(nom.WithTheme(nom.Theme{
    Running:   lipgloss.Color("#bd93f9"),  // purple (truecolor)
    Completed: lipgloss.Color("#50fa7b"),  // green
    Pending:   lipgloss.Color("#6272a4"),  // dim blue
    Failed:    lipgloss.Color("#ff5555"),  // red
}))

// Option 3: Auto-detect terminal background via OSC 11
sub := nom.NewNOMStyleSubscriber(nom.WithAutoTheme())

Theme struct replaces the global

type Theme struct {
    Colors  SemanticColors    // status → color mapping
    Symbols SemanticSymbols   // status → glyph mapping
}

The Colors global becomes the default theme, used when no WithTheme is passed. The TUI reads from the subscriber's theme instead of importing nom.Colors directly. One source of truth, configurable.

Auto-Detection

Query the terminal via OSC 11 (background color query) — if the background is dark, use a dark theme; if light, use a light theme. This is what ls and bat do. The x/term package already in the dependency tree can probe this.

Implementation

  • WithTheme(theme Theme) SubscriberOption — stores on subscriber
  • Renderers read theme from subscriber/config snapshot, not the global
  • TUI delegates: tui/colors.go reads from nom.Theme on the subscriber
  • WithAutoTheme() probes OSC 11 at startup, selects light or dark preset
  • Existing global Colors becomes the fallback when no theme is set
Verdict: Table stakes for a library that wants adoption. Every successful CLI tool has theme support. Medium effort because every renderer reads Colors.* — all need to route through the theme. But the change is mechanical, not architectural.

13Category Tints (Orthogonal Color Axis)

Novel Tier 2 Medium Effort

The Problem

Currently status is the only visual dimension. A node is green (completed), yellow (running), gray (pending), or red (failed). In a 20-node pipeline, all completed nodes look identical — you can't visually distinguish "build" tasks from "test" tasks from "deploy" tasks at a glance.

The Idea

Status and category are independent axes. Status determines the symbol + primary color (as today). Category provides a secondary visual dimension — a subtle tag prefix or background tint. The eye can scan vertically and see "all build tasks are green-ish, all test tasks are blue-ish" regardless of their status.

◈ Pipeline ├── ⏵ [build] Compile 4.2s ← green-tinted (build category) ├── ⏵ [test] Unit Tests 8.1s ← blue-tinted (test category) ├── ✔ [build] Lint 1.1s ← green-tinted └── ○ [deploy] Push Image ← orange-tinted (deploy category)

How It Works

type ActivityCategory string  // "build", "test", "deploy", "lint", ...

// On ActivitySnapshot:
Category ActivityCategory

// Theme maps categories to tint colors:
type Theme struct {
    Colors         SemanticColors
    Symbols        SemanticSymbols
    CategoryColors map[ActivityCategory]color.Color
}

The renderer applies the status color to the symbol, and the category color to a [tag] prefix or a faint background tint. Empty category = no tint (backward compatible).

Why nom can't do this

nom has no category concept — every derivation looks the same. A Nix derivation is just a build; there's no "test" vs "deploy" distinction in the derivation model. go-output's general-purpose activities can carry arbitrary metadata, making category tagging natural.

Implementation

  • Add Category ActivityCategory to Activity and ActivitySnapshot
  • SetCategory(id, cat) accessor on subscriber
  • Renderer: if category is set and has a tint color, render [tag] prefix
  • Theme: CategoryColors map[ActivityCategory]color.Color
  • Optional: CategoryBackground bool — use tint as background instead of prefix
  • Category can be inferred from phase membership (children of "Tests" phase get "test" category)

Advanced: Category-Based Collapse

With categories, the height-pressure collapse becomes smarter — instead of collapsing by phase, collapse by category. "All 6 build tasks passed" can become a single summary line regardless of tree structure.

Verdict: The differentiator that nom can't copy. Medium effort — needs a new field on Activity/ActivitySnapshot, a renderer change, and theme support (depends on idea #12). But the visual impact is immediate and striking.
