DAG data model — SecondaryParents eliminated

ActivityNode now stores Deps []ActivityID — ALL real dependency edges. Parent/Children are display-layout only, computed at Build() time. The SecondaryParents field, hasSecondaryParent() method, and the ← inline annotation are all deleted. Every reference across the entire codebase has been updated. Files: nom/tree.go, nom/tree_modification.go

Deepest-parent placement strategy (matching nom)

Build() now runs a fixpoint depth computation (longest path from root), then picks each node's deepest dep as DisplayParent. This matches nix-output-monitor's "lowermost dependency" rule — shared deps sink toward the leaves where they logically belong, instead of dangling off an arbitrary dependencies[0]. Files: nom/tree_building.go (rewritten: resetDisplayState(), computeDepths(), assignDisplayParents())

Option A — clean tree, no annotation (default)

The default rendering mode. Each node appears exactly once, under its deepest parent. No ← suffix, no clutter. This is what nom, cargo, bazel, and every major build tool does. The progress display's job is "what's happening now," not "what depends on what."

EWhat We Should Improve

!
Deepest-parent tie-breaking is arbitrary When two deps have the same depth, the first one in Deps order wins. This is deterministic but not semantically optimal — a "most recently completed" or "same phase" heuristic might produce better trees.
!
Build() is called lazily but not cached invalidation-safe AddActivity sets loaded = false, but Build() always recomputes from scratch (reset + fixpoint). For large DAGs with frequent AddActivity calls (e.g. streaming event handlers), this is O(n×iterations) per build. An incremental depth-update would help, but the current DAG sizes (<100 nodes) don't justify it yet.
!
No cycle detection API The fixpoint guard prevents infinite loops but doesn't tell the caller "your DAG has a cycle." A HasCycle() method using DFS coloring would be trivial to add now that the topology is a real DAG.
!
Option B sub-line is not visible in TUI mode The TUI delegates rendering to tree.RenderVisibleEntry() which calls renderLine() — so Option B IS visible. But the TUI's scroll logic (visibleEntries[treeLine]) assumes one entry = one row. The \n in the sub-line creates a multi-row entry that could misalign click mapping. This needs verification.
!

GThe One Question

Should the layered/topological display mode (Option C) be built?

During the DAG analysis, I identified layered/topological grouping as the one approach nobody in the terminal-progress space has seriously tried. It would group nodes by dependency depth (Kahn's algorithm waves), showing parallel-safe layers explicitly:

Layer 0 | ◈ Build ---------|--------------------------- Layer 1 | ○ Compile ○ Lint ---------|--------------------------- Layer 2 | ○ Test (needs: Compile + Lint)

The infrastructure (computeDepths()) now provides the depth data for free. The question is: is this a display mode users would actually want?

It's novel, it solves the multi-dependency visibility problem structurally (position encodes dependency, not annotation), and it maps to how CI/CD pipelines are designed. But it's a fundamentally different mental model from the tree, and it costs significant rendering work (new view mode, TUI integration, scroll logic). It's also unclear whether the nom-inspired aesthetic should diverge this far from the reference tool.

I cannot figure out myself: whether the user wants go-output to be a faithful nom clone (tree + dedup, period) or a tool that innovates beyond nom's design (layered mode, critical path, true DAG visualization). This is a product direction question, not a technical one.
