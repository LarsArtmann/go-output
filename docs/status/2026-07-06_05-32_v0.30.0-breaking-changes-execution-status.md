## B. PARTIALLY DONE ⚠️

### C11-C15: Renderer Structs Still Exist (by design)

The CQRS pure-function API was added alongside the existing renderer structs (DOTRenderer, MermaidRenderer, PlantUMLDiagram, ASCIITreeRenderer, MarkdownTable). The structs remain as **implementation detail** backing the pure functions. The decision record's "Appendix A: CQRS" vision called for deleting the structs entirely. The current approach is additive (new API layered on top) rather than replacing (old API removed). This is a deliberate trade-off: less churn, backward compatibility within v0.30.0, but not the full CQRS vision.

## E. WHAT WE SHOULD IMPROVE 🎯

1. **CQRS is additive, not replacing.** The old renderer structs still exist alongside the new pure functions. The full CQRS vision calls for deleting the structs and making them internal implementation. This should be the next major refactor — but it requires updating every consumer.

2. **RenderOptions struct is a relic.** Root's `RenderTable(data, fmt, RenderOptions{...})` uses a rigid options struct while everything else uses functional options. This should be unified.

3. **No `WriteXxx` for delimited/serialization/markup.** These modules already write to `io.Writer` internally but don't export standalone `WriteCSV(w, t)`, `WriteJSON(w, t)` functions. They only expose `MarshalCSV(t)` which returns bytes.

4. **Godoc examples missing for CQRS API.** The new `graph.RenderDOT(g)` / `d2.Render(diagram)` / etc. don't have `Example()` functions yet. This hurts discoverability on pkg.go.dev.

5. **No cross-shape projection functions.** The conversion logic exists internally but isn't exposed as clean `output.TableToGraph(t)` functions. Consumers have to use the lower-level `NodesFromTable` + manual builder.

6. **D2 prefix comments are stale.** Some doc comments in `ids.go` and `direction.go` still reference `d2.D2NodeID` and `d2.D2Direction` in comment text (the type aliases still exist as re-exports from root, but the comment text is misleading).

7. **CQRS doesn't yet use immutable Graph in renderers.** The pure functions convert `Graph` → `GraphBuilder` → renderer internally. The real CQRS flow should be `Graph` → renderer directly, without the intermediate builder.

## G. TOP #1 QUESTION 🤔

**Should the old mutable renderer structs (DOTRenderer, MermaidRenderer, PlantUMLDiagram, ASCIITreeRenderer, MarkdownTable) be DELETED in v0.30.0, or kept as a transitional layer?**

The decision record's Appendix A says "delete" — every renderer becomes a pure function. But:

- These structs are used by consumers' code (constructors, SetXxx methods, Render())
- Deleting them means every consumer must migrate to the CQRS API immediately
- The structs are the implementation backing the new pure functions

The current approach (additive: new API on top of old structs) is safer. Full deletion should probably be v0.31.0 or v1.0.0 with a deprecation cycle. **What does the user want?**
