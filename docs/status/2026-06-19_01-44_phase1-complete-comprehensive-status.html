04Totally Fucked Up

Bug · False claim in TODO_LIST

Subscriber tests pollute real ~/.cache/nom-timing.csv

nom/timing_cache.go:34-45 · nom/subscriber_test.go:188

What's broken: TestNOMStyleSubscriber_WorkflowStarted fails intermittently with "failed to read cache file: record on line 357: wrong number of fields". The real ~/.cache/nom-timing.csv had a truncated entry (4264068 with no activity name).

Why it's fucked up: TODO_LIST.md:62 claims this is "Fixed — newTempTimingCache(t) uses t.TempDir()". That fix only isolated direct TimingCache unit tests. The subscriber tests create a subscriber via NewNOMStyleSubscriber(), which calls NewTimingCache(), which always reads from ~/.cache/nom-timing.csv (line 40: filepath.Join(homeDir, cacheDir, cacheFilename)). There is no injection point for the cache path.

Impact: Any corrupted cache entry from real usage (or prior test run) breaks the entire nom test suite. This is a test-isolation defect that makes the suite non-hermetic.

Fix needed: Add WithCachePath(path string) option to NOMStyleSubscriber, or make TimingCache.filePath overridable via functional option. Then subscriber tests inject t.TempDir().

05What We Should Improve

1. Make tests hermetic

The timing-cache test isolation is the #1 priority. No Go test suite should read/write to real ~/.cache. Inject the cache path via functional option.

2. Brand the nom IDs (Phase 2)

ActivityID/WorkflowID should be phantom-branded like GraphNodeID/D2NodeID. Eliminates an entire class of ID-mixing bugs at compile time.

3. Gate commits with Go checks

Pre-commit should run gofumpt + go vet + golangci-lint. Currently only treefmt (Nix formatting) runs. Broken Go code ships to CI.

4. Complete the README

7 of 18 modules listed. A v1.0 library's README is its front door. Every module should be discoverable.

5. Add enum methods to ActivityStatus

Parse()/IsValid()/AllowedValues() — match the pattern already used by Format and Shape. Enables config-driven status parsing.

6. Store benchmark baselines

Benchmarks run but output is discarded. benchstat comparison against a stored baseline would catch performance regressions before they ship.

7. Type the Symbol constants

SymbolRunning etc. should be type Symbol string, not bare string. Prevents mixing symbols with arbitrary strings.

8. Write RELEASE.md

The 18-module mono-version bump process is undocumented. A new contributor (or future you) will struggle to cut a release.

07#1 Question I Cannot Figure Out

Decision Required

Should TableData use exported fields or getters for v1.0.0?

TODO_LIST.md #15 · Blocked — needs owner decision

This is the sole release blocker. The current API has both:

Option A (fields only): Remove getters (GetHeaders(), GetRows(), GetData()). Keep Headers, Rows, Footer. Simpler, more Go-idiomatic, but loses validation — callers can set mismatched column counts. Breaking for getter consumers.

Option B (unexported + setters): Unexport fields, add validated setters. Type-safe but the most breaking change. Every consumer's field-access code breaks.

Option C (keep both): No breakage in v0.x, but the dual API is a permanent smell. Every future maintainer asks "which do I use?"

Why I can't decide: This is an irreversible commitment. Once v1.0.0 ships, the public API is frozen. Each option has real tradeoffs that only the project owner can weigh: simplicity vs safety vs breakage. A wrong choice compounds forever.
