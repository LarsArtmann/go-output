Layered rendering output has no golden snapshot. A golden test would lock the visual layout and catch regressions in layer separators, header formatting, and priority ordering.

2. VT emulator test for layered mode

No TestVT_ test feeds layered-mode output through the VT emulator. Inline rendering of layered mode in a real terminal is untested at the screen-buffer level.

Theme.CategoryColors exists and Theme.CategoryColor() works, but the renderer doesn't apply category tints to activity labels yet — only the [tag] prefix is rendered. The tint should blend with or override the status color.

07G) THE #1 QUESTION

Strategic

Should layered mode become the DEFAULT rendering mode for BuildFlow integration?

The current default is RenderModeTree, which preserves backward compatibility with nix-output-monitor's layout. Layered mode makes parallelism explicit and is arguably more useful for DAG-aware build systems like BuildFlow — but it changes the visual output every existing user sees.

I cannot figure out: whether BuildFlow's users rely on the specific tree layout (parent/child connectors, indentation depth) for mentally tracking build phases, or whether they'd welcome the layer-based layout as a strict improvement. This is a product decision that depends on user feedback I don't have access to.

Recommendation: Ship layered mode as opt-in (WithRenderMode) for v1, gather feedback, then consider making it default in v2. But this is your call.
