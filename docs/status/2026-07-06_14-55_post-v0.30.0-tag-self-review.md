## E. WHAT WE SHOULD IMPROVE 🎯

### 1. Tag Only After ALL Fixes Are Committed

Tagging should be the LAST action, not an intermediate step. The tag force-push could have been avoided.

### 2. Test Error Values, Not Just Output Content

The WriteASCII bug existed because tests only checked `buf.String()`, never `err`. Every CQRS `WriteXxx` function needs a test asserting `err == nil` on the happy path. I added some error-writer tests, but the happy-path-nil-assertion gap may exist in other modules.

### 3. The CQRS Functions That Still Create Old Structs Internally Are a Code Smell

`WriteMermaid`, `WriteASCII`, `markdown.Write`, `plantuml.Write` each create their respective old renderer struct internally. This means the old struct can't be deleted without first extracting the rendering logic into a free function. This is Phase 1 of the v0.31.0 plan.

### 4. `RenderOptions` Struct Is a Relic

Every CQRS function uses functional options. The root dispatch uses a struct. This should be unified — either convert `RenderTable` to accept `opts ...RenderOption`, or accept that the registry dispatch is a different API surface.

### 5. No Integration Test for `tree.RenderMarkdown` or `tree.WriteMarkdown`

I added unit tests and a godoc example, but no cross-module integration test proving the markdown output works end-to-end with a TreeBuilder→RenderMarkdown pipeline.

### 6. Stale gopls Warnings Never Definitively Resolved

The `wsl_v5` and `makezero` IDE warnings on `projections.go`, `table_builder.go`, `tree_builder.go` persist in the IDE but `golangci-lint` passes with 0 issues. I confirmed they're stale via authoritative lint, but never restarted gopls or investigated WHY the cache is stale.

## G. TOP #1 QUESTION 🤔

**Should the v0.31.0 old-struct deletion be done incrementally (one struct per PR) or as a single big-bang deletion?**

The decision record (`docs/planning/2026-07-06_v0.31.0-old-struct-deletion-plan.md`) outlines 3 phases but doesn't specify the commit strategy. Arguments:

- **Incremental (one struct per PR):** Easier to review, easier to bisect if something breaks, smaller blast radius. But each PR is "delete one struct + update callers" — tedious, and the structs are interdependent (e.g., `NewDOTFromTable` returns `*DOTRenderer`, so deleting DOTRenderer means deleting the constructor too).
- **Big-bang (single PR):** One clean break. All structs, constructors, and converters deleted at once. All examples and tests migrated. More churn in one commit but the transition is clean — there's no "half-deleted" state.

**I lean toward big-bang** because the structs are interdependent and the migration path is already documented. But I can't fully assess this because I don't know if any external consumer (beyond BuildFlow, which doesn't use these structs) depends on them.
