## E) WHAT WE SHOULD IMPROVE 🔧

### Architecture
1. **Renderer interface unification** — `Renderer`, `TableRenderer`, `TreeOutputRenderer`, `GraphRenderer` are 4 separate interfaces. Could we unify with a generic `Renderer[T]` pattern? Risk: over-abstraction.
2. **Error wrapping consistency** — Some renderers wrap errors with context, others don't. Should standardize on `fmt.Errorf("render X: %w", err)` everywhere.
3. **ColorMode in all renderers** — Currently only table, tree, markdown support ColorMode. JSON/YAML/XML/HTML/CSV/TSV ignore it (which is correct), but there's no explicit `ColorMode` documentation per format.
4. **Streaming interface adoption** — Only HTML has a streaming renderer. JSONL has `JSONLWriter` but doesn't implement `StreamingRenderer`. Could unify.

### Developer Experience
5. **No `go generate` support** — Enums are hand-written. Could use `stringer` or `go-enum` for auto-generation.
6. **No `example_test.go` for most modules** — Only d2 and graph have runnable examples in Go doc.
7. **Test helper duplication** — `gentest` is root-only, so d2/graph/serialization all inline their own helpers.

### Operations
8. **CI doesn't run coverage threshold** — `golangci-lint` has no minimum coverage check. Should add `-coverprofile` with threshold enforcement.
9. **No release automation** — Tagging is manual. Could use GoReleaser or GitHub release workflow.
10. **CHANGELOG.md maintenance** — Entries are manual. Could use `git-cliff` or conventional commits auto-generation.

## G) TOP #1 QUESTION FOR LARS 🤔

**Should we target v1.0.0 next, or continue adding features at v0.x?**

The API surface is mature (16 formats, 13 modules, stable Shape/Format/ColorMode enums, registry dispatch). But:
- 4 exported interfaces (`Renderer`, `TableRenderer`, `TreeOutputRenderer`, `GraphRenderer`) — are these frozen?
- `TableData` is the central data type — is the `Headers/Rows` model sufficient, or do we need typed columns?
- The registry dispatch (`RegisterTableDataMarshaler`) is the main extension point — is this the right abstraction for v1?

If v1.0.0 is the target, I'd recommend: API audit → document stability guarantees → tag v1.0.0 → community launch.
