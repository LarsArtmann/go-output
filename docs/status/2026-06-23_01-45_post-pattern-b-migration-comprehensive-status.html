05What We Should Improve

1. No GOWORK=off CI test

Pattern B relies on replace directives. Local nix run .#test passes because go.work resolves everything. But we never test what an external consumer sees. A GOWORK=off go build ./... job in CI would catch any replace-masking issue immediately.

2. Stale git tags for deleted modules

16 tags exist for enum/ and envdetect/ (v0.6.1 through v0.17.1). They point to valid historical code that compiles, but the modules no longer exist on master. Consumers who pinned these tags will not break, but new consumers might be confused. Need a strategy: retract, delete, or document-and-leave.

3. testhelpers version lag

The ONE real-versioned sub-module is 5 minor versions behind (v0.13.0 vs v0.18.0). If testhelpers gains any breaking change, consumers at v0.13.0 will be stuck. Needs a retag at every release, or reconsider whether it should also go Pattern B.

4. Missing retract directives

No retract directives in any go.mod. If a broken version is ever published, there's no mechanism to warn consumers. Should add retracts for any known-bad historical versions as a safety net.

5. No property-based / fuzz testing beyond MarkdownTable

Only FuzzMarkdownTable exists. The escape module (10 functions across 6 formats) would benefit from fuzz testing. The nom snapshot model is a prime candidate for property-based testing (invariant: snapshot never races with mutation).

6. Integration tests don't cover every format × shape combination

16 formats × 3 shapes = 48 combinations. Integration tests cover many but not all. A systematic matrix test would catch edge cases in cross-shape conversion (TableData→Graph, Tree→Graph, etc.).

07The #1 Question I Cannot Answer Myself

Needs Owner Decision

What do we do with the 16 stale git tags for deleted enum/ and envdetect/ modules?

enum/v0.6.1 through enum/v0.17.1 (13 tags) and envdetect/v0.13.0 through envdetect/v0.17.1 (3 tags) still exist on the remote. They point to valid, compilable historical code. The modules themselves were merged into root and deleted from master in v0.18.0.

Three options, each with tradeoffs I cannot evaluate without you:

  • Leave them — consumers who pinned enum@v0.17.1 still build. But new users who find these tags on pkg.go.dev will be confused (module exists but no longer maintained).
  • Retract them — add retract directives. But retract directives must live in the module's own go.mod, and these modules are deleted. We'd need to create a minimal stub go.mod with just the retract, or retract from root (which doesn't work for sub-module paths).
  • Delete them — git tag -d + git push --delete. Clean, but breaks any consumer who pinned these tags. Destructive and irreversible.
My question: Do you have any external consumers depending on go-output/enum or go-output/envdetect as independent imports? If yes → leave the tags. If no → I recommend deleting them (the proxy cache will still serve them to existing consumers, but new consumers won't find them).
