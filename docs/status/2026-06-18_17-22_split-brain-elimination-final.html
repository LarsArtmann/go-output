05What We Should Improve

Type Model

Typed Events — Replace string routing + 7 accessor interfaces

The current event system uses string-based routing (`OnEvent` → `GetEventType() string` → switch on string) with 7 type-assertion accessor interfaces. A sealed `Event` interface + exhaustive type switch would eliminate the silent-typo-drop failure mode and ~60 lines of accessor boilerplate. This is the highest-impact remaining architectural improvement.

Trade-off Changes the `EventSubscriber` interface contract. Any external implementers would break. Viable as a 0.x minor breaking change or as a backward-compatible addition (keep `GetEventType()` as a legacy method alongside the new sealed interface).
Test Gap

Cross-module color agreement test

No executable contract asserts root `ShouldColor()` and nom `detectNoColor()` agree. A table-driven test in `integration/` that iterates env-var combinations would catch regressions if `envdetect/` logic ever drifts from the callers.

Cleanup

tui consumes `nom.Colors` instead of maintaining `terminalColors`

The `SemanticColors` struct is available in nom. The `tui` module (which depends on nom) could consume it directly instead of maintaining its own `terminalColors` struct with duplicate ANSI codes. This is a cleanup, not a bug — the values are already aligned.

Cleanup

Unify "No activities to display" to single source

Both `nom` and `tui` define the same string. Since `tui` imports `nom`, it could re-export `nom.msgNoActivitiesToDisplay` (or nom could export it). Low priority — the constants are already aligned in value, just not in canonical location.

Test Gap

Add `FormatDuration` fuzzing for edge cases

The `FormatDuration` function (in `nom/format.go`) handles sub-minute, minute, hour, and day boundaries. A fuzz test would verify no panic on negative, zero, or extremely large durations, and would catch regressions in the "60.0s" boundary fix that was already shipped.

07Top #1 Question I Cannot Figure Out

BLOCKING

Should the typed-events refactor happen as a 0.x breaking change or a backward-compatible addition?

The current event system uses string-based routing (OnEvent → GetEventType() string → switch on string) with 7 type-assertion accessor interfaces. Replacing it with a sealed Event interface + exhaustive type switch would eliminate the silent-typo-drop failure mode.

But:

  • It changes the EventSubscriber interface contract — any external code implementing Event with GetEventType() string would break
  • The nom.Event* constants are now all in place and properly used (zero bare literals)
  • The accessor interfaces are ugly but working
  • The bdd/ module tests events via the string API
Option A (breaking, 0.x minor) Replace Event with sealed interface; remove GetEventType(). Clean, correct, but breaks external implementers.
Option B (backward-compatible) Keep GetEventType() string as a legacy method; add new sealed Event interface alongside. No breakage, but maintains two event systems in parallel.

I lean toward Option A (breaking) because the current system is genuinely fragile (a typo in a string silently drops an event), and we are in 0.x where breaking changes are expected. But I need your call on timing — is now the right window, or should this wait until after a release candidate?
