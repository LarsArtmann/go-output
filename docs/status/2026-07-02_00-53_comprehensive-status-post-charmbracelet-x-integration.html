05(e) What We Should Improve

Deepen E2E test assertions

Current teatest tests verify "program doesn't crash" but not "program renders correct content". Feed teatest output through x/vt to assert on actual screen cells.

Remove 3 unused test helpers

snapshot(), has() in nom, errWriteFailed in table. Trivial cleanup — just delete the dead code.

Add nom example to README

The NOM inline renderer is the most impressive feature but the README focuses on table/tree output formats. A NOM example would showcase real-time progress for CLI tools.

PhysicalLineCount integer-division approximation

nom/terminal.go:33 computes line wrapping via integer division of StringWidth by terminal width. This is approximate — wide characters and combining marks can cause off-by-one. cellbuf would fix this but is deferred.

tree/ and markdown/ hand-rolled ANSI

10 hand-rolled \033[...m SGR constants across tree/tree.go and markdown/markdown.go. Correct but doesn't support 256-color/true-color. Kept for dependency-lightness — revisit if these modules ever need rich color.

No coverage threshold enforcement

782 tests is substantial but there's no CI coverage gate or coverage report. Adding -coverprofile + a threshold would catch regressions.

07(g) The #1 Question I Cannot Answer Myself

Should we ship v1.0.0 now, or wait for deeper E2E test coverage?

The API is frozen (ADR 006). All 18 modules build, test, lint, and race-clean. 782 tests exist. The codebase has 9 ADRs, 173 features (161 fully functional), and zero open bugs. By every objective measure, this is v1.0.0-ready.

But: the TUI E2E tests are shallow (they verify the program loop works but not that specific content renders correctly). The VT tests cover the InlineRenderer deeply but the TUI View() path is only indirectly tested. If we ship v1.0.0 now, we commit to API stability for code whose TUI rendering has thin E2E coverage. If we wait, we risk never shipping (perfect is the enemy of shipped).

This is a business judgment call, not a technical one. Only the project owner can weigh the risk of v1 API lock-in against the momentum cost of delaying the release.

My recommendation if asked

Ship v1.0.0 now. The TUI E2E depth is a post-release improvement, not a release blocker. The API surface (output formats, table/tree/graph types, NOM events) is stable and well-tested. The TUI rendering paths can be deepened without breaking API changes. Waiting for "perfect testing" before v1 is how projects die in perpetual beta.
