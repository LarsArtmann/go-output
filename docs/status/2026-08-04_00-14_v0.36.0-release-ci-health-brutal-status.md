### 2. Is `art-dupl` v0.6.1 a published release you control, or did someone else break it?

The CI `Code Duplication Check` job fails because `go install github.com/LarsArtmann/art-dupl/cmd/art-dupl@latest` pulls v0.6.1 which has compilation errors (`undefined: cloneGroupFull`, etc.). Since it's under `LarsArtmann`, it's your repo — but I don't know if v0.6.1 was published broken intentionally or if the module path changed. Should I pin to an older version, or will you fix art-dupl itself?

> **✅ Resolved 2026-08-04:** art-dupl is Lars's repo. Root cause: `report.templ`'s generated `report_templ.go` was gitignored and never committed. Fixed by generating + committing the file, tagging v0.6.2, and pinning CI to `@v0.6.2`.

### 3. Should the TUI race tests (`TestProgressModel_RenderRacingActivityMutation`, `TestProgressModel_RenderDependencyTree_CollapseMarkerNoPanic`) be `t.Parallel()` at all?

These tests deadlock at `t.Parallel()` — they sit in `chan receive` for 9+ minutes waiting for something that never arrives. The test code calls `t.Parallel()` then does event dispatching that appears to need the test goroutine to proceed. This looks like a test design issue, not a production code bug. Should I investigate the deadlock root cause, or do you already know why these tests can't run in parallel?

> **✅ Resolved 2026-08-04:** Root cause was NOT `t.Parallel()`. The deadlock was in `TestTeatest_VTScreen_ShowsActivityLabels` — `teatest.WaitFor` uses `io.ReadAll` on a buffer the program writes to continuously; under `-race` it never sees EOF and blocks past the 10min test timeout. Fixed by replacing `teatest.WaitFor` with a bounded polling helper (`pollTeatestOutput`) that drains the buffer with fixed-size reads + a hard deadline.
