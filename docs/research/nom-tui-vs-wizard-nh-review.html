Implementation status

All recommended improvements have been implemented and verified (go test ./... and golangci-lint run ./... pass for nom/ and tui/).

  • Priority-ordered child sorting: children at each tree level are now sorted failed → running → paused → pending → completed, with elapsed time and activity ID as tie-breakers.
  • Width truncation + physical line accounting: long lines are truncated with …; InlineRenderer now tracks wrapped physical lines for correct in-place redraws.
  • Median timing estimates: TimingCache now uses median instead of mean for robust duration estimates.
  • On-demand refresh + 1s max-frame: InlineRenderer.Refresh() triggers immediate redraws; the background loop also renders at least once per second so timers stay current.
  • Terminal-state summary line: InlineRenderer.Finish reports elapsed time and success/failure; TUI NOM summary bar is colored by workflow state.

Key insight up front

The goal is a generic CLI progress UI for visualizing multiple concurrent activities — not a nix tool. NOM's rendering techniques (dependency tree, in-place ANSI redraw, status symbols, timing estimates) are the inspiration; NOM's nix-specific machinery (JSON parsing, per-host transfer tracking, derivation interning, .drv reading) is out of scope and deliberately not copied.

nh contributes nothing here — it shells out to nom as a subprocess (nix build --log-format internal-json -v | nom --json). Your design instead makes NOM-style rendering an in-process, event-driven Go library for any workflow. That's the real differentiator.

2. What go-output does well

Clean event-driven decoupling. EventSubscriber + type-assertion accessor interfaces (WorkflowEventAccessor, ActivityEventAccessor, DependenciesAccessor) let the subscriber avoid importing concrete event types. NOM has no equivalent abstraction — it's hardwired to nix's JSON schema. This is a genuinely good, reusable design.

Two output surfaces. InlineRenderer (no alt-screen, scrolls naturally — exactly NOM's mode) and tui.BubbleTeaProgressReporter (alt-screen, scrollable, mouse, help overlay). NOM offers only inline; nh offers neither. You have strictly more options.

Timing cache. CSV persistence, 10-entry cap, async saves — architecturally faithful to NOM's build-reports.csv.

Strong workflow state machine (tui.WorkflowState: Idle→Running→Completed/Errored, terminal states reject updates). NOM has only JustStarted|InputReceived|Finished. Yours is more robust.

lipgloss isolation in nom/ (the AGENTS.md module boundary discipline) keeps the dependency honest.

3. Rendering gaps that matter for concurrent activities

P0

Priority-ordered DFS is claimed but not implemented

This matters more for a generic concurrent-activity UI than for nix. When many things happen at once, screen space is the scarce resource: the user needs to see what's running and failing right now, not a wall of already-finished work. AGENTS.md claims "priority-based filtering (Running > Failed > Pending > Completed)", but the code doesn't do this. collectVisibleNodes (tree_render.go:59) walks roots sorted by activity ID string (tree_building.go:22), then children in insertion order, capping at maxHeight. So the first N nodes in tree order win — a long completed branch starves a currently-failing activity of visibility.

NOM's SortKey (SFailed < SBuilding < SDownloading < … < SDone) is exactly the right idea to port: rank by interest so the hot nodes always fit. This is the single highest-impact change for "easily see when multiple things are happening."

P0

No terminal-width handling / line truncation

InlineRenderer.effectiveMaxHeight handles height only. There is no width truncation, no wrapping prediction. NOM's truncateOutput truncates wide lines with … and, on overflow, shows first line + ⋮ + last 5 lines. With deep trees your lines overflow silently and break the in-place redraw math (cursor-up count vs. actual wrapped lines diverge → screen corruption). This is also a latent bug in your prevLines accounting.

P1

In-place redraw is naive vs. NOM's

Aspect go-output InlineRenderer NOM
Redraw trigger Fixed time.Ticker interval 60ms min-frame + 1s max-frame + refresh_display_var signal — redraws on demand and at least once/sec for timers
Per-line movement Rewrites every line each frame (ansiClearLine + line) howToGoToNextLine: StayInLine / MoveToNextLine (no scroll) / PrintNewLine — minimizes work
Tearing None iTerm2 synchronized updates (\x1b[?2026h/l) for flicker-free atomic frames
Line-clear choice \r\033[K per line clearLineCode deliberately avoiding clearFromCursorToScreenEnd ("triggers a flush on some terminals")
Write batching Multiple fmt.Fprint in Finish loop; one string in Render One pre-built ByteString, single hPut + hFlush

Your fixed-ticker model means either wasted redraws (busy) or stale timers (too slow). Consider an event-signaled + max-interval hybrid.

P1

Estimation uses mean, NOM uses median

timing_cache.go:74 GetAverage = arithmetic mean. NOM takes the median of the last ≤10 runs (NOM.Update). Median is robust to outliers (one cold-cache build skews your mean heavily). Easy win.

P2

Summary bar is intentionally simpler — that's correct

Your renderSummary is a single boxed line (⏵3 ✔2 ⚠1 ⏸4 ⏱1.5s ∑10). NOM renders a dense multi-column table with separate Builds/Downloads/Uploads columns and per-host rows. That complexity is nix-specific (builds vs transfers vs remote hosts) and out of scope for a generic activity UI. Your compact status bar is the right call — one glance shows how many are running/done/failed/pending. The only worthwhile addition: a terminal-state line (Finished after 3m42s / ⚠ Exited after N failures) since that's universally useful, not nix-specific.

P2

No subtree-aggregate caching

NOM precomputes a DependencySummary monoid per node and propagates changes up derivationParents — O(log n) summary updates instead of full-tree recompute each frame. Your getActivityCounts (view.go:321) iterates all activities every tick. Fine at small scale; worth noting.

4. vs. wizard-tutorial (Bubble Tea idioms)

Your tui/ already follows the tutorial's core patterns correctly and goes beyond it. Comparison:

Pattern wizard-tutorial your tui/ Verdict
State representation index into []Question WorkflowState enum + displayMode + scroll offset ✓ Yours is richer & typed
Sub-model delegation Input interface wrapping textinput/textarea nomSubscriber sync + per-mode renderNOMStyle/renderUniversalWorkflowProgress ✓ Equivalent discipline
Program options WithAltScreen() only AltScreen + MouseModeCellMotion + lazy start ✓ You exceed it
Debugging tea.LogToFile (alt-screen owns stdout) log.Printf to stderr ⚠ In alt-screen mode, stderr logging can corrupt the frame — consider tea.LogToFile when AltScreen=true
Transition logic Next() increments/wraps index CanTransitionTo state machine ✓ Stronger

The wizard teaches form collection (step→input→enter→next). Your DisplayModeUniversal "nh darwin switch" step tree is a different problem (progress, not input), so the direct overlap is small. The one transferable lesson: tea.LogToFile for alt-screen debugging.

5. vs. nh — confirming the integration stance

nh treats NOM as an external subprocess (nix … | nom --json), checking the first process's exit code (nom always exits 0). nh itself contains zero rendering code. That works for nh because NOM is a finished, nix-specific binary and nh only ever needs nix progress.

Your design is different and stronger for the generic case: NOM-style rendering as an in-process, event-driven Go library driven by a generic EventSubscriber interface. Any Go program reports activities via typed events; the library renders them. No subprocess, no nix coupling, no shared output format to parse. This is the right call for a reusable progress UI — the integration stance is already correct; no decision needed.

The practical implication: focus effort on rendering quality for many concurrent activities (priority ranking, clean in-place updates, good defaults) rather than chasing NOM's nix-specific feature surface (per-host tables, transfer byte-counters, derivation interning, .drv parsing). Those don't generalize and aren't worth porting.
