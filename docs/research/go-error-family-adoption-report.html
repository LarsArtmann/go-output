PRO/CONTRA: Adopting go-error-family in go-output

Research Report · 2026-06-01 · Evaluating github.com/larsartmann/go-error-family v0.3.0 for github.com/larsartmann/go-output

Executive Summary

Verdict: Do Not Adopt (Yet)

go-error-family is an excellent library for CLI applications and HTTP services that need structured error classification, retry semantics, and CLI exit codes. However, go-output is a formatting library, not a CLI application. Its error surface is 89% I/O context wrappers and 11% validation sentinels — none of which benefit from Family classification, retry hints, or exit codes. Adoption would add complexity without solving a real problem go-output has.

Recommended instead: Recommend go-error-family to go-output's consumers (CLI apps) via documentation/examples. Consider adopting only if go-output adds CLI boundary features (e.g., an output.Run() entry point with exit codes).

PRO Arguments

1. Standardized Error Construction Architecture Medium Impact

go-output has 6 custom error types with inconsistent field structures: InvalidFormatError has Allowed []Format; InvalidShapeError only has Value string; UnsupportedFormatError uses a typed Format field. go-error-family would provide a uniform construction pattern via New(family, code, msg) and family-specific shortcuts.

But: This benefit is cosmetic. The inconsistency exists because each error type carries domain-specific fields (allowed values, format type). Replacing them with errorfamily.NewRejection("format.invalid", "bad format") would actually lose structured metadata like Allowed []Format.

2. Better Examples / Developer Experience API Medium Impact

The examples/ directory uses os.Exit(1) for all errors. Showing errorfamily.HandleError(err) in examples would demonstrate how to properly handle go-output errors at the CLI boundary with meaningful exit codes. This is the strongest adoption argument: dogfooding a sibling library.

But: This can be achieved by adding go-error-family as a dependency in the examples/ module only, not in the core library. The examples module already has its own go.mod and is not imported by consumers.

3. Future-Proofing for CLI Boundary Features Scope Low Impact

If go-output ever adds a output.Run() or output.Main() entry point that combines rendering + error handling + exit codes, go-error-family's HandleError() and ExitCode() would be directly useful.

But: This is speculative. go-output's stated purpose is "a reusable Go library for CLI applications providing consistent output formatting" — it formats output, it doesn't run applications. Adding CLI boundary features would be scope creep.

CONTRA Arguments

1. Domain Mismatch: Library vs. Application Scope High Impact

go-error-family's core value proposition is classifying errors into families (Retry, Exit Code, Audience, Tone). This classification is meaningful at the CLI/HTTP boundary — where errors leave your program and meet a human.

go-output is a formatting library. It sits deep in the call stack. Its errors are "write row failed" and "invalid format". Classifying these as Transient vs Infrastructure is meaningless — the caller's CLI boundary should make that decision, not the formatting library.

Analogy: Using go-error-family in go-output is like installing a customer support ticketing system in a printer driver. The printer reports "out of paper". The ticketing system belongs at the help desk, not in the driver.

2. Dependency Philosophy Violation Dependencies High Impact

go-output's architecture document states:

"Root has ZERO sub-module imports" and "go get github.com/larsartmann/go-output pulls ZERO lipgloss deps, ZERO yaml deps..."

Adding go-error-family to root's go.mod would introduce a new transitive dependency for every consumer. While the library itself is zero-dep, the principle matters: a formatting library should minimize its dependency footprint.

If added only to sub-modules (d2/, delimited/), the error types would be inconsistent across modules. If added to root, it's a philosophy violation. There's no clean placement.

3. Semantic Mismatch with 89% of Errors Architecture High Impact

74 out of ~83 fmt.Errorf calls are pure I/O context wrappers:

  • "write row: %w"
  • "flush tsv writer: %w"
  • "marshal json (%T): %w"
  • "render markdown: %w"

These are "what was happening when it failed" context, not error contracts. Wrapping them with errorfamily.NewTransient("io.write", "write row") would add zero value — the caller still can't retry a half-written CSV. The underlying io.ErrShortWrite is what matters, and it's already available via %w.

Making these into classified errors would actively hurt readability. Currently: write row: io: read/write on closed pipe. With adoption: [transient:io.write] write row: io: read/write on closed pipe. No one benefits from the prefix.

4. Go 1.26 Floor Requirement API Medium Impact

go-error-family requires Go 1.26+ (uses errors.AsType[T]()). go-output also targets Go 1.26+, so there's no conflict today.

But: Adopting it couples go-output's Go version floor to go-error-family's floor. If go-error-family moves to Go 1.27 for future features, go-output would be forced to follow. Currently, go-output only couples its floor to its own needs + enum/x/term.

5. Lost Structured Metadata API Medium Impact

Current error types carry domain-specific structured data:

  • InvalidFormatError{Value, Allowed []Format} — consumer can inspect allowed values
  • UnsupportedFormatError{Format} — consumer can inspect the unsupported format
  • TableData.Validate() returns errColumnMismatch with column counts

go-error-family's Error struct has Code (string) and Context (map[string]string). To preserve the same metadata, you'd need to stuff everything into WithContext("allowed", "csv, json, ...") — losing type safety. Allowed []Format becomes "allowed" => "csv,json". This is objectively worse for programmatic consumers.

Conditional / Neutral Arguments

6. Zero External Deps (Library Itself) Dependencies

go-error-family has zero external dependencies (pure stdlib). This makes it the lightest possible dependency. No transitive supply chain risk.

Neutral because: zero deps is a necessary condition, not a sufficient one. The question isn't "is it cheap?" but "is it useful?"

7. Consistent Error Formatting API

go-error-family's fmt.Formatter gives %v (compact), %+v (verbose with context/timestamp/chain), %s (message only). This is nicer than go-output's current flat strings.

Neutral because: go-output's errors are rarely formatted beyond %v in examples. The verbose format would be useful at CLI boundaries, but that's the caller's job.

8. Same Author / Same Ecosystem Maintenance

Both libraries are by the same author (github.com/larsartmann). Cross-module compatibility is guaranteed by design. Breaking changes would be coordinated.

Neutral because: same-author dependency is a double-edged sword. It reduces coordination overhead but creates coupling that may bias architectural decisions.

Recommendation

Do: Strategy B — Examples Only

Add go-error-family as a dependency in the examples/ module only. Replace shared.HandleError() with errorfamily.HandleError(). This demonstrates best practices to consumers without polluting the core library.

Do not add it to root or any sub-module's go.mod. Do not replace existing error types. Do not implement errorfamily interfaces on existing structs.

go-error-family belongs at the CLI boundary. go-output is a formatting library. They are complementary but should not be coupled.
