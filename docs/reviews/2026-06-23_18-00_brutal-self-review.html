01What I Forgot

1. PlantUML had the same injection vulnerability

I wrote injection regression tests for D2, DOT, and Mermaid — then stopped. PlantUML's plantumlColorSpec() wrote Fill/Stroke/FontColor raw, allowing semicolons to inject attributes and newlines to inject arbitrary PlantUML syntax. Same vulnerability class, same fix pattern, same test pattern — and I missed it entirely. Fixed: added plantumlColorValue() with escape.PlantUML() + semicolon replacement.

2. CODE_OF_CONDUCT.md was silently deleted

The BuildFlow pre-commit hook deleted it in commit 622e7dc (before my session). I documented the hook behavior in AGENTS.md but never verified the file still existed. It was gone for 8+ commits. Fixed: restored from 622e7dc^.

3. Injection tests were half-strength

My D2/DOT/Mermaid injection tests only verified "raw malicious value doesn't leak" — a negative assertion. They never checked that the correct escaped sequence appeared in the output. An escaper that deletes the value entirely would pass. Fixed: added TestD2NodeStyleEscapeOutput, TestDOTNodeStyleEscapeOutput, TestMermaidNodeStyleEscapeOutput with positive assertions for exact escape sequences.

4. Scroll optimization had zero regression tests

I replaced the entire NOM scroll rendering pipeline (render-entire-tree-then-clip → entry-level windowing) without a single test verifying scrolling behavior. The existing tests checked scroll offset mechanics but not scroll rendering output. Fixed: TestProgressModel_ScrollRendering_ShowsCorrectWindow verifies offset=0 shows first page, offset=5 shows different window, scrollToBottomSentinel clamps correctly.

5. scrollOffset not reset on display mode switch

Switching from NOM (tree-scrolled) to Universal (step-based) carried the stale offset, landing mid-content. The field was shared between modes but never reset. Fixed: SetDisplayMode() now resets scrollOffset = 0.

02What Was Stupid

1. I stopped at 3 renderers when there are 4

The self-review plan said "D2/DOT/Mermaid" — and I followed it literally without checking "wait, are there other renderers with the same pattern?" There are 4 graph renderers: D2, DOT, Mermaid, PlantUML. PlantUML was the obvious miss. The fix was 3 lines of code. The test was 30 lines. I should have searched for ALL plantumlColorSpec/writeNodeAttr/mermaidStyleParts patterns in one sweep, not cherry-picked from the plan.

2. I treated negative assertions as sufficient

"Raw value doesn't appear" is necessary but not sufficient. A function that returns "" passes. I should have written positive assertions from the start — "the escaped sequence DOES appear" — in the same test. This is Testing 101 and I skipped it.

04What Remains (Not Blocking)

go-branded-id vs go-composable-business-types

The how-to-golang skill recommends go-composable-business-types for branded types. The project uses go-branded-id across all 18 modules. This is a large migration with no functional difference today — branded IDs already provide compile-time type safety. Would align with skill guidance but isn't urgent.

RenderWithSnapshots still collects all entries on scroll

My scroll optimization improved rendering from O(all) to O(visible), but entry collection is still O(all) — VisibleEntriesWithSnapshots(snapshots, 0) walks the entire tree. A VisibleEntriesRange that skips before offset and stops after height would be truly O(visible), but requires non-trivial tree-walk rework.

chromeLines is a magic number

chromeLines = 8 is hardcoded but derived from the actual chrome layout (title=2, message=1, summary=1, section gaps=3, treeStart=1). Should be computed or at least documented with the arithmetic.

samber/lo could simplify makezero conversions

Many of the make([]T, 0, n) + append patterns I wrote could be lo.Map(src, func(t T, _ int) U { ... }). The project doesn't use samber/lo yet — adopting it would simplify ~15 slice-building sites.

06Type Model Ideas

ColorValue branded type

The injection vulnerabilities all stem from raw string flowing into style fields. A branded ColorValue type that validates at construction (hex pattern or named color) would make injection impossible at the type level — GraphStyle.Fill would be ColorValue, not string. Callers would construct via NewColorValue("#ff0000") which validates.

RendererStyle interface for per-format escaping

Each renderer already has its own escaping logic. An interface like type StyleEscaper interface { EscapeColorValue(string) string } on the renderer would centralize the escaping per-format and make it testable without rendering a full diagram.

07Library Opportunities

samber/lo — slice utilities

Recommended by how-to-golang skill. Would replace 15+ manual make+append loops with lo.Map. Already used in other LarsArtmann projects.

samber/mo — option/either types

For GraphStyle.FontSize which uses 0 as "unset" (can't distinguish 0pt from absent). mo.Option[int] would make "not set" explicit. Same pattern applies to D2NodeStyle.Opacity which was just fixed to allow 0.0 as a valid value via != 0 instead of > 0 — the real fix is an optional type.
