01P1 — Concurrency Bugs in nom/

nom/ is the most complex package and the one with real concurrency. It mostly gets the hard parts right (the documented two-mutex model is sound, the snapshot model killed a real data race, goroutine shutdown in the render loop is correct). But config reads outside the snapshot path and disk I/O under the subscriber lock are genuine bugs. These are the highest-impact items in the whole review.

C1. Data race: r.appName read without lock in RenderCompletion

nom/inline_renderer.go:816 · vs SetAppName at :244

RenderCompletion reads r.appName directly while holding only renderMu. But SetAppName writes it under tickMu. These are two different mutexes by design — the AGENTS.md explicitly warns they "MUST stay separate." Every other config read in Draw/Finish goes through snapshotConfig() (one tickMu.RLock), but RenderCompletion was missed. A concurrent SetAppName + RenderCompletion is a race the -race detector will flag.

Fix: read via cfg := r.snapshotConfig() and use cfg.appName.

C2. Subscriber write-lock held across disk I/O

nom/subscriber_handlers.go:57 & :68

handleWorkflowStarted holds ns.mu.Lock() across ns.timingCache.EnsureLoaded() (a file read). handleWorkflowFinished holds it across ns.timingCache.Save() (a file write). This blocks all subscriber operations — OnEvent, SnapshotActivities, GetActivityCounts — for the duration of disk I/O. On a slow filesystem or NFS mount this stalls the entire render loop.

Fix: drop ns.mu before the I/O call (load into a local, call EnsureLoaded/Save unlocked), or move the cache load/save off the hot event path entirely. EnsureLoaded is already internally lock-free — only the caller holds the big lock.

C3. renderNotify field accessed without synchronization

nom/inline_renderer.go:728 & inline_renderer_test.go:261

renderAndNotify() reads r.renderNotify (a channel) with no lock. Tests write it directly. If a test sets it while the render loop runs, the race detector fires. Channel field reads need the same protection as every other config field — route through snapshotConfig or guard with tickMu.

C4. saveAsync spawns unbounded goroutines, never drained in production

nom/timing_cache.go:102-103

Every Record() call (one per completed activity) spawns a fresh goroutine: go tc.saveAsync(). saveMu serializes the disk writes, so under a workflow with many fast activities the goroutines pile up waiting on the mutex. The pendingSaves WaitGroup is tracked, but waitPendingSaves() is unexported and only called from tests — production never waits, so goroutines can outlive the subscriber and writes can race with process exit (truncated cache file).

Fix: a single background saver goroutine fed by a buffered channel, with a Flush()/Close() on the subscriber that waits for drain. This also batches writes (one save per flush window instead of N).

C5. saveAsync swallows errors via log.Printf

nom/timing_cache_persist.go:160-162

A failed cache write is logged and dropped. Record() already returns error but ignores the async save entirely. Silent cache corruption with no caller recourse. Library code logging instead of returning is explicitly an anti-pattern in the project's own conventions. Surface this as a returned error or a documented best-effort-save contract.

C6. r.subscriber.showParallelism read without subscriber lock

nom/inline_renderer_summary.go:145

Direct field read on NOMStyleSubscriber from the renderer, no ns.mu. It's benign in practice (the field is only set at construction via WithShowParallelism), but it breaks the locking discipline the rest of the package follows and sets a trap for anyone who later makes it mutable. Either document it as construction-only-immutable, or snapshot it.

02Dead Code & Ghost Systems

The project has a habit of shipping features before they have consumers. Each item below was verified by grep + gopls to have zero production callers. Some are speculative (RegisterStatus, the extra themes) — these are ghost systems: code that exists, is tested in isolation, but proves no real workflow. Per the project's own rule: a ghost system should be integrated or deleted. Target for dead exported API: zero.

D1. RegisterStatus() — flagship extensible-status API with zero callers Ghost System

nom/status_registry.go:102

The entire status-registry extensibility story (ADR 011) is shipped, documented, and never used. RegisterStatus() is called only in status_registry_test.go. No example, no integration test, no real consumer demonstrates a custom status ("skipped", "cached") flowing through the full render pipeline. This is the textbook ghost system: a feature built on speculation with no proven value. Either write a real consumer (example binary) or move it behind an experimental flag until someone needs it.

D2. ThemeNord & ThemeMonochrome — dead and untested

nom/theme.go:117 & :139

Two of the five documented theme presets have zero callers anywhere (code, tests, examples) and zero test coverage. ThemeDracula is in an example, ThemeHighContrast in the auto-theme path — these two are decoration. Delete, or add a smoke test + example if the Nord palette is genuinely wanted.

D3. ErrActivityNotFound — exported, never returned

nom/tree.go:11

var ErrActivityNotFound = errors.New("activity not found") is part of the public API but no method ever returns it. GetNode returns nil on a map miss, not an error. Dead exported symbol that misleads callers into writing errors.Is(err, nom.ErrActivityNotFound) checks that can never match. Delete it, or make GetNode actually return it (preferred — nil-on-miss is itself a mild footgun).

D4. TimingFormat constant — unused

nom/format.go:12

const TimingFormat = "%.1fs" — its own comment says "used by FormatDuration()" but FormatDuration() (line 15) uses integer math and never references it. The comment is a lie. Delete the constant.

D5. Activity.IsPhase() — zero callers

nom/activity.go:139

The *Activity method is dead. Every call site uses snap.IsPhase() (the snapshot value copy) or kind.IsPhase() directly. The snapshot model means *Activity methods are rarely the right call anyway. Delete it.

D6. ActivityNode.hasDep() — gopls-confirmed unused

nom/tree.go:149

Sibling methods hasChild and removeChild are used; this one was left behind. gopls flags it as [gopls unusedfunc]. Delete.

D7. EdgeStyle.ArrowHead / ArrowTail — never read by any renderer

graph.go:189-192

Two public string fields on a core type that DOT, D2, Mermaid, and PlantUML all ignore. Only referenced in graph/graph_test.go. This is a false API — users will set these expecting arrow styling and get nothing. Either wire them into the renderers or remove them.

D8. SymbolUpload — dead in production

nom/symbols.go:32

Referenced only in an example binary and the symbol-uniqueness test. No rendering path emits it. If uploads aren't a real concept yet, this is speculative palette. Keep only if a consumer is imminent.

D9. Unused parameter physicalLines in buildLogAndTreeOutput

nom/inline_renderer.go:500 · gopls [unusedparams]

The sibling buildRedrawOutput uses physicalLines for ghost-line cleanup; this function silently ignores it. This is a latent bug, not just dead code: a shrinking tree with pending enqueued logs will leave ghost lines because the cleanup count is dropped. Wire it in or document why it's safe to ignore here.

D10. Dead test helpers assertScreenNotContains / assertRowEmpty

Test-only dead code, but it rots the harness. Delete or re-wire.

03Split Brains

Two sources of truth for the same concept. The project has worked hard to eliminate these — here are the ones that survived.

S1. Identical constant msgNoActivitiesToDisplay defined in two packages

nom/tree.go:17 & tui/constants.go:16

Both packages define an unexported constant with the same name and value "No activities to display". The nom comment even says "Mirrors tui.MsgNoActivitiesToDisplay" — but that exported symbol does not exist. A prior status report literally called this a "half-assed fix." Define it once (root or nom) and export it; both packages import the single source.

S2. Global var Colors bypasses the Theme system

nom/symbols.go:78 vs nom/theme.go:82

The package-level var Colors = SemanticColors{...} is still read directly in production (status_registry.go:44,57,70,83, activity.go:161, activity_status.go:55). But the Theme system (ThemeDefault.Colors = Colors) is supposed to be the single source — the whole point of v0.23.0 themes was that themed values resolve at snapshot time. The global is a second path that ignores theme overrides. A user who sets WithTheme(ThemeDracula) will still get default-blue status colors in the registry paths. Route all color reads through the theme.

S3. Duplicate accessor: DependencyTree() vs GetDependencyTree()

nom/nom_subscriber.go:230 & nom/state_accessors.go:24

Two exported methods return the exact same field, both used across tests, examples, and integration. Redundant API surface. The project already removed Get-prefix smells elsewhere (GetOperationSymbol → OperationSymbol). Pick one (the project convention is no Get prefix), deprecate the other with a clear removal target.

S4. D2Direction and output.Direction — two enums for one concept

d2/d2_enum.go:13 vs direction.go:8

ADR notes claim this was "fixed — added output.Direction," but both enums still exist with full Parse/IsValid/AllowedValues APIs, and Direction.ToD2Direction() returns a bare string, not a D2Direction — so they don't interoperate type-safely. The bridge exists but is stringly-typed. Collapse to one enum; have d2/ reference output.Direction directly.

S5. AGENTS.md documents SymbolOverrides; the real field is Symbols

AGENTS.md (Theme section) vs nom/theme.go:23

The primary onboarding doc tells every new session the theme struct field is SymbolOverrides map[ActivityStatus]Symbol. The actual field is Symbols. Anyone copy-pasting from AGENTS.md gets a compile error and loses trust in the doc. (This is a doc lie, listed here because it's a name split-brain between doc and code.)

04Stupid Patterns

P1. StreamingRendererFromRenderer is a false-promise adapter

streaming.go:24

It implements StreamingRenderer by calling Render() (builds the entire string in memory) then writing it in one shot. That is the opposite of streaming. The type name promises incremental output that never happens, and it's only used in a test. Either make it actually stream (chunked writes) or rename it to RendererAsWriter so it stops lying about its behavior.

P2. D2NodeStyle.TextTransform is stringly-typed

d2/d2.go:47

Every other D2 style field was converted to a typed enum with Parse/IsValid/AllowedValues. This one accepts a bare string ("uppercase"/"lowercase"/"capitalize") with no validation. Inconsistent with the package's own pattern. Add a TextTransform enum.

P3. DependencyTree.Build() error always returns nil

nom/tree_building.go:8

The signature forces every caller to handle an error that can never happen. Worse, the fixpoint loop in computeDepths has a max-iteration guard against cycles but never reports one — so the cycle is silently swallowed instead of surfaced as the error the signature already promises. Either drop the error return, or make cycle detection actually return it (preferred — silent cycles are nasty to debug).

P4. InlineRenderer.write() silently drops ALL I/O errors

nom/inline_renderer.go:594

_, _ = fmt.Fprint(r.writer, s). Intentional for broken-pipe resilience — fine — but there's no way for a caller to ever detect a permanently-dead writer (closed pipe). The renderer will spin its refresh loop forever writing to nowhere. At minimum, count consecutive failures and self-Stop after a threshold.

P5. Draw() cyclomatic complexity 20 — the only lint failure

nom/inline_renderer.go:357

golangci-lint cyclop fails the build on this one function (max 12). It handles 8 orthogonal concerns in sequence: nil guard, empty-tree bail, pending-only drain, summary append, frame-diff skip, plain-text mode, zero-lines bail, inline redraw + TTY sync gate. The plain-text path (406-430) and inline path (432-464) share no logic. Extract shouldSkipDraw() bool, drawPlainText(...), drawInline(...). This is the single thing standing between the project and a clean lint — and it's a 30-minute refactor.

P6. Naming smells: NOMStyleSubscriber & SemanticColors.Info

nom/nom_subscriber.go:22 & nom/symbols.go:69

NOMStyleSubscriber — the Style infix adds no information; NOMSubscriber is cleaner and the type name appears in every option doc. SemanticColors.Info is the fallback color for unknown statuses — "Info" doesn't correspond to any activity concept; Fallback or Unknown would say what it means. Both are cosmetic but the project holds itself to a naming bar.

08The Self-Review Questions

1. What did we forget?
To treat the nom/ concurrency code with the same discipline as the rest of the package. The snapshot model is right, but config reads outside it (C1, C3, C6) and disk I/O under the subscriber lock (C2) were missed because they're not on the hot render path the snapshot model was designed for. Also: docs drifted (L1–L4) because releases shipped without a doc-sync step.
2. What's something stupid we do anyway?
Ship speculative features with zero consumers (RegisterStatus, ThemeNord/Monochrome, SymbolUpload, EdgeStyle arrow fields). It violates the project's own YAGNI rule and every one of them is a maintenance liability with no proven value. "Built but unused" is the most expensive kind of code.
3. What could we have done better?
Treat the timing cache as a real subsystem: a single background saver with Flush(), error surfacing, and shutdown ordering — instead of unbounded goroutines + swallowed log.Printf. And decompose Draw() the moment cyclop flagged it, instead of leaving the only lint failure in the project sitting for weeks.
4. What could we still improve?
Everything in the execution plan. Concretely: zero lint failures, zero dead exported API, zero split-brain constants, zero doc lies, and a pruned docs/status/. The target state is reachable in ~1 day.
5. Did I lie to you?
The docs did — TODO_LIST claims things that aren't true (L1–L3). I did not: every finding in this report was verified against the live code with build/lint/test/gopls/grep. The "all green" claim in recent status reports is almost true — tests and build are green, but lint has one failure and there are 6 latent race conditions.
6. How can we be less stupid?
Two process changes: (a) a "consumer or delete" gate before merging any new public API — if there's no caller in the repo or an example, it doesn't ship; (b) a doc-sync checklist item on every release that re-greps TODO_LIST/FEATURES/AGENTS against reality. Both are cheap and kill the two recurring failure modes in this review.
7. Ghost systems — are we building any?
Yes. RegisterStatus() + the whole status-registry extensibility (ADR 011) is a ghost system: implemented, tested in isolation, documented, and used by nobody. It has theoretical value (custom statuses) but zero proven value. Recommendation: build one real consumer (example binary + integration test rendering a "skipped" status end-to-end) before v1.0.0, otherwise it's speculative surface area on a "frozen API."
8. Are we in the scope-creep trap?
Slightly. v0.23.0 added layered mode, themes, categories, critical-path, parallelism meter, DAG summary, and daghtml in one release — a lot of surface area at once, some of it unused (the two themes). The core (16 formats × 3 shapes) is stable and complete; the nom/tui layer is where creep is happening. Recommend a consolidation sprint (this plan) before new nom features.
9. Did we remove something that was actually useful?
No clear regressions found. The removals documented in TODO_LIST (SortBy, FormatCategory, OutputFormat alias, ActivityStore) were all genuinely dead and the replacements are sound. Nothing to restore.
10. Did we create any split brains — even small ones?
Yes, five (S1–S5). The most consequential is S2: the global Colors bypassing the Theme system means themed status colors don't fully apply — that's a user-visible inconsistency hiding behind a "single source of truth" claim. The rest are constant/accessor/doc duplications.
11. How are we doing on tests? What can we do better?
Strong overall: VT-emulator harness, teatest/v2 E2E, fuzz, golden files, race tests — above industry average. Gaps: (a) RegisterStatus() has no integration test proving custom statuses render; (b) ThemeNord/ThemeMonochrome have zero coverage; (c) the concurrency bugs (C1–C6) aren't caught because the race tests don't exercise SetAppName/RenderCompletion or disk-I/O-during-event concurrently. Add a race test that calls every config setter concurrently with Draw/Finish/RenderCompletion — that would have caught C1/C3/C6 immediately.
