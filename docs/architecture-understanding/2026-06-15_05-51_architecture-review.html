1. Questions Answered

How scalable/modular is the current architecture?

Highly modular. The library is split into 16 Go modules with hard, compile-time-enforced boundaries. Root (package output) holds only core types + Markdown/Tree formatters. Every format family lives behind its own go.mod, so consumers import and download only what they use. go get github.com/larsartmann/go-output pulls zero lipgloss, bubbletea, yaml, or toml dependencies.

How can we make this more service-oriented / composable?

As a library, "service-oriented" maps to interface-driven composability — already strong here. Three seams drive composition: the Renderer interface family, the registry-dispatch pattern (RenderTableData), and the shape capability matrix. Recommendations in §5.

4. Composability Seams

① Renderer interface family

Renderer → TableRenderer → GraphRenderer → TreeOutputRenderer. Every format implements one. MustRender(r) for tests. Deep, uniform seam.

② Registry dispatch

RenderTableData() / RenderAnyData() dispatch to format functions registered in init(). Root has zero sub-module imports; sub-modules self-register. Excellent inversion.

③ Shape capability matrix

Format.Supports(Shape) + FormatsForShape(). Single source of truth for "can format X render shape Y". Enables validation and discovery.

④ GraphRendererState

Shared composition state embedded by DOT/Mermaid/JSON/YAML/TOML/PlantUML. AddTreeNodes() via NodeEdgeAppender interface. Reused, not duplicated.

5. Findings

Strengths

  • Radical dependency isolation. Root imports only enum in production. Heavy deps (lipgloss, bubbletea, yaml, toml) are hermetically sealed in their modules.
  • Self-registering formats. Zero coupling between root and format modules — the registry pattern means root never imports delimited/serialization/etc. in production.
  • Standalone resolvable. Every module builds with GOWORK=off via committed replace directives. True independence, not just workspace convenience.
  • Type safety everywhere. Branded phantom IDs (D2NodeID vs TreeNodeID) prevent mixing at compile time.
  • Minimal duplication. art-dupl reports "Excellent code health" — only test idioms, one actionable clone.

3 Registry uses "Marshaler", everything else "Renderer" — mild terminology split-brain for the same concept. Cognitive friction for new contributors Low

5 nom/inline_renderer.go ignores write errors (6 unchecked fmt.Fprint) — a renderer whose job is writing drops errors. Broken pipe / disk-full silently swallowed Medium

7. Verdict

GRADE A — Production-ready architecture

The go-output architecture is genuinely excellent for a multi-format Go library. Module boundaries are correct, dependencies flow one direction, heavy libraries are sealed away from the core, and the registry-dispatch + shape-matrix design is a model of composable, interface-driven Go. The gaps are minor (lint config portability, write-error handling, one coarse module) — none threaten the architecture's soundness. This is a codebase that has clearly been thought about, not just written.
