① TableData: enforce invariants at the seam

Strong

tabledata.go · core domain type

Problem. The TableData module has a wide mutation interface and its invariants are checked post-hoc. Its fields (Headers, Rows, Footer) are exported and mutable, and it offers setters (SetFooter), and getters (GetHeaders/GetRows/GetFooter) — three surfaces for the same data. Worse, AddRow silently accepts mismatched column counts while AddRowChecked validates; the safe and unsafe paths coexist by design. Validate() only runs at render time, so a TableData can exist in an invalid state for its whole lifetime. Every method also guards a nil receiver — a representable-but-invalid state.

Solution. Unexport the fields. Route all mutation through validated methods (SetHeaders, AddRow that always validates, SetFooter). Column-count mismatch becomes a compile-time-impossible state rather than a runtime check. Delete AddRowChecked (the unchecked path) and Validate() (now provably unnecessary). Keep the getters only if interface contracts (TableDataProvider) require them.

Benefits. Locality: the column-count invariant lives in one place (the constructor + setters), not scattered across every renderer that calls Validate(). Leverage: callers can never build broken data. Test surface: tests assert "you cannot construct mismatched data" rather than "Validate catches it". The deletion test passes for AddRowChecked + Validate() — their complexity is pure defense against a self-inflicted wound.

Before — shallow, post-hoc

type TableData struct {
  Headers []string   // exported, mutable
  Rows    [][]string // exported, mutable
  Footer  []string   // exported, mutable
}
AddRow(r)        // no validation ❌
AddRowChecked(r) // validates     ✅
Validate()       // render-time   ⏰
// nil *TableData representable

After — deep, enforced

type TableData struct {
  headers []string  // unexported
  rows    [][]string
  footer  []string
}
SetHeaders(h)        // sets width
AddRow(r) error      // always validates
SetFooter(f) error   // validates width
// mismatch = impossible state
// Validate() deleted — unneeded

⚠️ Breaking change (exported fields, AddRow signature). Defer to post-v1 or gate behind a v2 TableData. ADR 006 conflict — but the friction is real.

② InlineRenderer ↔ NOMStyleSubscriber: one deep module?

Worth exploring

nom/inline_renderer.go · nom/subscriber.go

Problem. To render NOM progress you must instantiate two tightly-coupled modules: a NOMStyleSubscriber (holds the DependencyTree + TimingCache) and an InlineRenderer (reads the subscriber's tree, writes to a writer). The InlineRenderer's interface is broad — 8 methods (Start/Stop/Finish/Render/SetAppName/SetNoColor/SetHideCursor/SetStartTime) — yet it has no behaviour without the subscriber. They are never used apart. This is a hypothetical seam with exactly one adapter combination.

Solution (to explore). Consider a single deep NOMProgress module whose interface is OnEvent (feed) + Render (draw) + Finish. The tree, cache, and writer all become internal seams. The two-adapter test: is there a second way to consume the subscriber (e.g. the BubbleTea path in tui/)? Yes — tui reads the subscriber's tree directly. So the subscriber seam is real; the InlineRenderer is the shallow part. Deepening target: keep the subscriber, fold the InlineRenderer's format logic into a deeper render module or make it a thin adapter with a smaller interface.

Before — two coupled modules

sub := NewNOMStyleSubscriber(...)
r   := NewInlineRenderer(sub, w, width)
r.SetAppName("x"); r.Start()
sub.OnEvent(ctx, ev)
r.Render(); r.Finish()
// 8-method interface on renderer
// renderer meaningless without sub

After — deep render module

sub := NewNOMStyleSubscriber(...)
p   := NewProgress(sub, w, width)
p.OnEvent(ctx, ev)   // feed
p.Render()           // draw
p.Finish()
// 3-method interface
// tree+cache+writer = internal

③ StreamingRendererFromRenderer: pass-through adapter

Speculative

streaming.go

Problem. StreamingRendererFromRenderer(r) adapts a Renderer (returns string) into a StreamingRenderer (writes to writer) by rendering fully then writing — i.e. it does not actually stream. Deletion test: deleting it, callers that need streaming either use a real streaming renderer or write io.WriteString(w, r.Render()) themselves. The complexity it hides is one line.

Verdict. One adapter = hypothetical seam. It earns its keep only if there are multiple callers that need this exact bridge and find the one-liner noisy. Check call sites; if few, inline it.

🏆 Top recommendation

Candidate ① — TableData invariant enforcement is the highest-value deepening, but it is breaking and blocked by ADR 006 until post-v1.

For now, the non-breaking, high-locality win is Candidate ②: collapse the InlineRenderer's 8-method interface behind a smaller render seam once the subscriber/tree split is confirmed as the real boundary (it is — tui/ proves a second consumer exists).

Neither is urgent — the codebase is already well-architected. These are the few places where the interface carries more than its share of the complexity.
