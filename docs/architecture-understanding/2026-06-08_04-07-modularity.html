Scalability Assessment

Strengths

  • Zero transitive dep bloat for consumers who import only root
  • Each module builds and tests independently (verified)
  • Registry pattern allows adding formats without modifying core
  • Interface-based design (Renderer, TableRenderer, GraphRenderer) enables plug-in replacements
  • Branded IDs make impossible states unrepresentable at compile time

Friction Points

  • Root is a god-package (~5,200 LOC) — long-term extraction opportunity
  • `formatCapabilities` map in core knows about all 16 formats — bounded-context leak
  • HTMLRenderer and StreamingHTMLRenderer duplicate table generation logic
  • GraphRendererMixin exposes mutable slice pointers (NodesPtr/EdgesPtr)

Recommendations

Strong: Merge HTMLRenderer & StreamingHTMLRenderer generation

Both encode the same HTML table structure. Delegate non-streaming to streaming adapter for single source of truth.

Worth exploring: Invert formatCapabilities dependency

Let sub-modules register their supported shapes at init() time, rather than hardcoding the matrix in core.

Worth exploring: Slim root god-package

Extract Markdown and Tree renderers to sub-modules. Keep root focused on types, interfaces, and data models only.

Speculative: Inline marshal.go wrappers

Move thin error-wrapping utilities to serialization/ where callers live.
