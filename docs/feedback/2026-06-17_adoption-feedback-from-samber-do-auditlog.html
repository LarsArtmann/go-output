What would make me adopt go-output

An honest, code-referenced review from the perspective of samber-do-auditlog — a DI container observability plugin that exports dependency graphs as Mermaid, PlantUML, JSON, and interactive HTML. I wanted to use your library. Here's what stopped me, and what would change my mind.

◆What's already excellent

Before the criticism: this library gets a lot right. The architecture is thoughtful, the multi-module workspace is well-executed, and the escape package is genuinely best-in-class. These are the foundations that made me want to adopt it in the first place:

+
Multi-module isolation done right Lipgloss stays in table/, Bubble Tea stays in tui/. Importing the root pulls only x/term. This is the correct way to structure a formatting library.
+
The escape/ package is perfect Zero dependencies. MermaidID, MermaidText, SlugifyID, D2, DOT — all correct, all tested. I borrowed these concepts locally. This module alone is worth publishing standalone.
+
Shape capability matrix The Format → []Shape registry with f.Supports(shape) and FormatsForShape(shape) is elegant. Runtime format selection from CLI flags becomes trivial.
+
Branded phantom ID types GraphNodeID vs TreeNodeID vs D2NodeID — compile-time safety preventing ID mixups. This is the kind of type-level design most Go libraries skip.
+
Cross-shape conversion TableData → Graph, Tree → Graph — the SetNodesFromTableData and AddTreeNodes patterns make the data models composable rather than siloed.
The bottom line I declined to adopt go-output for diagram rendering. Not because it's bad — but because the diagram renderers are opinionated where they should be configurable, and configurable where they should be invisible. The escape package is the exception: it's exactly right. Fix the four issues below and I'd adopt it tomorrow.

01Critical gaps blocking adoption

These four issues are why I ship local code instead of importing your library.

Blocking · High impact

GraphStyle is dead code in Mermaid and PlantUML

graph/mermaid.go:51-78 · plantuml/plantuml.go:49-79

The GraphStyle struct exists with FillColor, StrokeColor, FontColor, and FontSize — but only the DOT renderer reads it. Mermaid ignores it entirely. PlantUML ignores it entirely. I verified this by grepping for Style, FillColor, and StrokeColor in both files: zero matches in Mermaid, only hardcoded skinparam in PlantUML.

Meanwhile, the Mermaid renderer hardcodes a pink classDef:

// graph/mermaid.go:73 — hardcoded, cannot be overridden
b.WriteString("    classDef default fill:#f9f,stroke:#333,stroke-width:4px\n")

My plugin uses a deliberate warm-amber palette (#e8a838 on #14110d) across its HTML visualization. Switching to go-output would replace that with pink. For any library whose value proposition includes visual consistency, this is a non-starter.

Fix: wire GraphStyle into all renderers Mermaid: emit style <node-id> fill:#xxx,stroke:#yyy per node when Style is set. PlantUML: emit individual skinparam or inline color directives. Also add a WithTheme(Theme) option for global defaults.
Blocking · Data correctness

No edge deduplication in GraphRendererState

graph.go:148-155 · AddEdge just appends

AddEdge is a raw append with no dedup. If a dependency graph produces duplicate edges (common with transitive dependencies), the rendered diagram shows visual noise — multiple identical arrows stacked on top of each other.

I tested this: adding A→B twice renders two identical edges. My plugin's local writeDiagram deduplicates via a seen map[string]struct{}. The consumer shouldn't have to implement this. 

// What the consumer has to do today:
seen := make(map[string]struct{})
for _, edge := range edges {
    key := edge.From.Get() + "->" + edge.To.Get()
    if _, ok := seen[key]; ok { continue }
    seen[key] = struct{}{}
    renderer.AddEdge(edge)
}

// What it should be:
renderer.AddEdge(edge) // dedup handled internally
Fix: add SetEdgesDeduplicated([]GraphEdge) or dedup in Render() A simple from + "->" + to key in a map[string]struct{} is all it takes. Optionally dedup on (from, to, label) to allow parallel edges with different labels.
Blocking · Output contract

Mermaid output is locked behind a markdown code fence

graph/mermaid.go:54 · b.WriteString("```mermaid\n")

MermaidRenderer.Render() wraps its output in ```mermaid ... ```. This assumes the output is going into a Markdown document. But many tools expect raw flowchart syntax: .mmd files, the Mermaid CLI, embedded diagrams in HTML, programmatic APIs. The fence is wrong for all of those. 

// Current output — fence is hardcoded, cannot be removed
```mermaid
flowchart TD
    a[b]
```

// What raw .mmd consumers need
flowchart TD
    a[b]
Fix: make the fence optional Add WithCodeFence(bool) (default false for raw output). Or provide RenderRaw() alongside Render(). The fence is a presentation concern, not a rendering concern.
Blocking · Module graph pollution

Importing any sub-module transitively pulls YAML + TOML dependencies

go.mod (root) · requires serialization v0.11.0

The README claims: "go get go-output pulls ZERO lipgloss deps, ZERO bubbletea deps, ZERO yaml deps, ZERO toml deps". This is true for the root module alone. But any sub-module import pulls the root as a dependency, and the root's go.mod requires serialization v0.11.0 — which transitively brings go-faster/yaml and go-toml/v2 into every consumer's module graph.

I measured this. Importing only graph + plantuml:

go-output/graph (what I wanted) └── go-output (root, required by graph) ├── go-output/serialization ← I never asked for this │ ├── go-faster/yaml v0.4.6 ← 7 transitive deps │ ├── go-toml/v2 v2.4.0 ← 0 deps but module bloat │ ├── go-faster/jx v1.2.0 ← JSON encoder │ └── segmentio/asm v1.2.1 ← assembly optimizations ├── go-output/enum ← fine ├── go-branded-id v0.3.1 ← fine └── golang.org/x/term ← fine 11 unwanted external modules for a diagram renderer

For a plugin whose entire value proposition is minimal-overhead observability, adding YAML and TOML libraries to the dependency tree for Mermaid output is a hard sell.

Fix: remove serialization from root go.mod requires The root package's source code doesn't import serialization in any non-test file. It's only in go.mod because go mod tidy detected it in examples/ and integration/ test helpers. Move those to a separate test module, or mark serialization as // indirect. The root should require only: enum, go-branded-id, x/term.

02Important gaps for production use

These wouldn't block a prototype, but they'd make me think twice before shipping.

Bug · Collision risk

SlugifyID doesn't handle dots, brackets, or asterisks

escape/escape.go:70-74 · only replaces space, hyphen, slash

SlugifyID replaces -/ with underscores — but not .*[]. Two services named foo.bar and foo_bar would produce identical slug IDs, causing a silent node collision in PlantUML (which uses SlugifyID for sanitizePlantUMLID). 

// Current replacer — missing . * [ ] { } ( )
var slugIDReplacer = strings.NewReplacer(
    " ", "_",
    "-", "_",
    "/", "_",
)

// Should be — cover all identifier-hostile chars
var slugIDReplacer = strings.NewReplacer(
    " ", "_", "-", "_", "/", "_",
    ".", "_", "*", "_",
    "[", "_", "]", "_",
    "{", "_", "}", "_",
    "(", "_", ")", "_",
)
Configurability

DOT renderer hardcodes layout attributes

graph/dot.go:84-87

rankdir=TB, splines=ortho, nodesep=0.5, ranksep=0.5 are all hardcoded. These are layout decisions the consumer should control. A left-to-right service graph needs rankdir=LR. A dense graph needs tighter spacing. The DOT renderer should expose these as configuration. 

// Current — hardcoded in Render()
b.WriteString("  rankdir=TB;\n")
b.WriteString("  splines=ortho;\n")
b.WriteString("  nodesep=0.5;\n")
b.WriteString("  ranksep=0.5;\n\n")

// Should be configurable
type DOTRenderer struct {
    output.GraphRendererState
    directed bool
    graphID  string
    rankdir  string  // "TB" (default), "LR", "BT", "RL"
    splines  string  // "ortho" (default), "spline", "polyline", "line"
    // ...
}
Scalability

All renderers return string — no io.Writer support for diagrams

renderer.go:4-7 · Renderer.Render() (string, error)

Every renderer returns (string, error). For large dependency graphs (500+ services), the entire diagram is buffered in memory before writing. StreamingRenderer exists but only HTML implements it. The diagram renderers should support io.Writer directly to avoid the string allocation.

Compounding factor The renderMermaidTableData function (mermaid.go:24) calls Render() to get a string, then fmt.Fprintln(w, out) to write it. That's a full double-buffer: builder → string → writer. For 500 nodes this is measurable.
Risk · Ecosystem

Pre-v1 with no stability promise for diagram APIs

All modules at v0.11.0

At v0.11.0 across a multi-module workspace, there's no stability guarantee. A consumer embedding go-output in a library that other people depend on needs to know the GraphRenderer interface won't break between minor versions. Consider documenting which APIs are stable (like the root Renderer interface) vs experimental (like D2's rich domain model).

03What the API could look like

If these four critical fixes were implemented, adopting go-output would be a net positive. Here's what the consumer experience would look like: 

// Today: 60 lines of local diagram code, zero deps
// Tomorrow: 15 lines, one import, full feature set

import (
    "github.com/larsartmann/go-output"
    "github.com/larsartmann/go-output/graph"
    "github.com/larsartmann/go-output/plantuml"
)

func WriteMermaid(w io.Writer, report Report) error {
    r := graph.NewMermaidRenderer()

    // Apply my theme — not pink defaults
    r.SetTheme(graph.Theme{
        PrimaryColor:   "#e8a838",
        PrimaryText:    "#14110d",
        PrimaryBorder:  "#4a4030",
        LineColor:      "#9a8d78",
    })
    r.SetDirection("TD")
    r.SetCodeFence(false) // raw flowchart, no markdown wrapper

    // Add nodes with per-node styling
    for _, svc := range report.Services {
        r.AddNode(output.GraphNode{
            ID:    output.NewBrandedID[output.GraphNodeIDBrand](svc.ScopeID + "_" + svc.ServiceName),
            Label: output.NewBrandedID[output.GraphNodeLabelBrand](svc.ServiceName),
            Shape: output.ShapeBox,
        })
    }

    // Add edges — dedup handled internally
    for _, svc := range report.Services {
        for _, dep := range svc.Dependencies {
            r.AddEdge(output.NewGraphEdge(svc.ServiceName, dep.ServiceName))
        }
    }

    out, err := r.Render()
    if err != nil {
        return fmt.Errorf("render mermaid: %w", err)
    }

    _, err = io.WriteString(w, out)
    return err
}
This is the target Theme injection, raw output, internal dedup, and a clean dependency tree. With these four fixes, go-output goes from "I'll borrow your escape package" to "I'll delete my diagram code and import yours."
