🧭 What is a "Split-Brain"?

A split-brain issue is when the same real-world concept is modeled in two or more places that can independently drift. It is the architectural root cause behind "I changed it here but forgot there" bugs. There are three flavors, all hunted in this audit:

  • Exact duplicates — same name & shape redefined in another package (silent drift risk).
  • Near-duplicates — different names but the same concept; a translation layer keeps them in sync by hand (brittle).
  • Multiple sources of truth — two live copies of the same data kept in sync manually (race-prone).

How to read severity: Critical = a true bug or data-integrity risk, fix now. Major = high drift risk, fix this sprint. Minor = acceptable but worth a note.

    Two completely different structs both named TreeNode

    output.TreeNode vs nom.TreeNode

    The exported name TreeNode is defined twice for unrelated concepts. Anyone importing both packages must qualify every reference, and code review cannot tell at a glance which tree a TreeNode belongs to.

    tree.go:19 nom/tree.go:14 
    // tree.go:19 — generic hierarchical node for diagram FORMATS (D2/DOT/Mermaid/PlantUML)
type TreeNode struct {
    ID TreeNodeID
    Label TreeNodeLabel
    Children []*TreeNode
    Metadata map[string]string
}

// nom/tree.go:14 — live activity-status tracker for the dependency tree
type TreeNode struct {
    DisplayState            // embedded activity status/timing
    ActivityID, ActivityName string
    Parent *TreeNode
    Children []*TreeNode
    SecondaryParents []ActivityID
    Depth int
    IsRoot, IsDisplayed bool
}

    ⚠️ Why it's dangerous

    The TUI module imports both. A field like node.Children resolves to a different slice type depending on which import the file pulled in. The names lie about what they are.

    ✅ How to fix

    1. Rename nom.TreeNode → nom.ActivityNode (it models an activity in the dependency tree, not a generic tree node).
    2. Use a project-wide find/replace scoped to the nom/ and tui/ packages.
    3. Run nix run .#test — the compiler will list every reference that needs updating.
    4. The root output.TreeNode stays unchanged (it is the canonical, generic one).
    C2 Critical Effort high

    ProgressModel holds a hand-synced copy of NOMStyleSubscriber state

    Two live sources of truth for activities · dependencyTree · timingCache

    The TUI model stores its own copies of the subscriber's internal maps and then manually re-syncs them every 100 ms tick. If the sync is ever skipped, reordered, or a new field is added to one side but not the other, the UI shows stale data.

    tui/state.go:109-117 tui/model.go:182-196 nom/nom_subscriber.go:9-22 
    // tui/state.go:109 — the model keeps its OWN copies…
type ProgressModel struct {
    activities     map[ActivityID]*ActivityDisplayState
    dependencyTree *DependencyTree
    timingCache    *TimingCache
    nomSubscriber  *NOMStyleSubscriber   // …AND the original owner
}

// tui/model.go:182 — manually re-synced every tick (race-prone)
func (m *ProgressModel) syncNOMSubscriber() {
    m.nomSubscriber.UpdateRunningActivityElapsed()
    m.nomSubscriber.SyncActivityTimingToTree()
    m.activities     = m.nomSubscriber.GetActivities()
    m.dependencyTree = m.nomSubscriber.GetDependencyTree()
}

    ⚠️ Why it's dangerous

    There are now two copies of the activity map and dependency tree alive in memory. Any render code that reads m.activities reads a snapshot that may be one tick behind the subscriber. Adding a new field to NOMStyleSubscriber silently leaves the model's copy out of sync.

    ✅ How to fix

    1. Remove the duplicated fields (activities, dependencyTree, timingCache) from ProgressModel.
    2. Replace every read of m.activities with a delegated call: m.nomSubscriber.GetActivities().
    3. Keep syncNOMSubscriber() only for the mutating calls (UpdateRunningActivityElapsed, SyncActivityTimingToTree) and the workflow-state transition logic.
    4. Cache locally only if a profiler proves GetActivities() is a hot-path cost — and then cache in one place with a clear // cached snapshot comment.
    C3 Critical Effort low

    TimingFormat — same name, different value, silent rendering mismatch

    nom.TimingFormat = "%.1fs" vs tui.TimingFormat = "⏱️ %.1fs"

    Two constants with the identical name format durations in seconds — but the TUI version embeds a ⏱️ emoji prefix while the NOM version does not. A developer searching for "TimingFormat" will assume they are equivalent. They are not.

    nom/format.go:32 tui/constants.go:6 
    // nom/format.go:32
const TimingFormat = "%.1fs"            // used by FormatDuration()

// tui/constants.go:6
const (
    TimingFormat = "⏱️ %.1fs"       // emoji baked into the format string
)

    ⚠️ Why it's dangerous

    NOM deliberately separates the symbol from the duration (SymbolTiming + FormatDuration() in nom/format.go:58). The TUI constant bakes the symbol in. "Fixing" one to match the other introduces a double-emoji or missing-emoji rendering regression with no compiler error.

    ✅ How to fix

    1. Decide on one canonical pattern: symbol separate from format string (NOM's approach is more flexible).
    2. Rename tui.TimingFormat → tui.timingFormatWithIcon (unexport it) OR delete it and compose "⏱️ " + nom.FormatDuration(t) at the call site.
    3. grep for every Sprintf(TimingFormat call to confirm nothing relied on the emoji being embedded.

    Three independent color systems for the same semantic colors

    root ANSI strings · tui lipgloss struct · nom lipgloss vars — green/yellow/red/gray each defined 2-3 times

    The same four semantic colors (green=success, yellow=warning/running, red=error/failed, gray=dim/paused) are defined independently in three modules with the same ANSI codes but different names. There is also an intra-package duplicate: nom.ColorWarning and nom.ColorRunning are the same value.

    color.go:12-20 tui/colors.go:27-38 nom/symbols.go:35-53 
    // SAME colors, THREE homes:
// root:  ansiGreen="\033[32m"   ansiCyan="\033[36m"   …  (raw escape strings)
// tui:   success: lipgloss.Color("10")  warning: lipgloss.Color("11")  err: lipgloss.Color("9")
// nom:   ColorCompleted=lipgloss.Color("10") ColorFailed=lipgloss.Color("9") ColorWarning=lipgloss.Color("11")

// BONUS intra-package duplicate in nom/symbols.go:
var ColorRunning = lipgloss.Color("11")   // :35
var ColorWarning  = lipgloss.Color("11")   // :47  ← identical value, different name

    ⚠️ Why it's dangerous

    If the design system changes "success" from green to teal, you must hunt three files. The root uses raw ANSI strings while nom/tui use lipgloss.Color — so the root colors and the lipgloss colors are not even comparable types.

    ✅ How to fix

    • Quick win: delete nom.ColorWarning (it equals ColorRunning); replace usages with ColorRunning.
    • Structural: create a shared nom.Theme type (lipgloss-based) that the tui package consumes, since tui already depends on nom. Move the 4 semantic colors there once.
    • The root raw-ANSI colors (ansiGreen etc.) can stay — they serve the zero-dependency root module — but document that they mirror the lipgloss values.
    M2 Major Effort low

    Two divergent "should I disable color?" detectors

    nom.detectNoColor() checks TERM=dumb + CI · root isNoColor()+isCI() checks 5 CI vars but NOT TERM=dumb

    Both functions answer the same question ("is color disabled?") with different rules, so the same terminal can be color-enabled for the root renderers and color-disabled for the NOM inline renderer.

    nom/inline_renderer.go:81-95 color.go:107-117 
    // nom/inline_renderer.go:81
func detectNoColor() bool {
    return os.Getenv("NO_COLOR") != "" ||
           os.Getenv("TERM") == "dumb" ||   // ← root does NOT check this
           os.Getenv("CI") != ""
}

// color.go:107  (root — separate module, can't import)
func isNoColor() bool { return os.Getenv("NO_COLOR") != "" }
func isCI() bool {
    return os.Getenv("CI") != "" || os.Getenv("GITHUB_ACTIONS") != "" ||
           os.Getenv("GITLAB_CI") != "" || os.Getenv("JENKINS_URL") != "" ||
           os.Getenv("BUILDKITE") != ""   // ← nom does NOT check these 4
}

    ✅ How to fix

    • The modules can't share code (root is zero-dep, nom is separate) — so the goal is identical logic in two places, clearly cross-referenced.
    • Align both to the union of checks: NO_COLOR + TERM=dumb + all 5 CI vars.
    • Add a comment in each: // Mirrors color.go isNoColor()+isCI(). Keep in sync.
    • Optional: add a shared test table in testhelpers/ of env-var combos that both detectors must agree on.

    M4 Major Effort medium

    Three incompatible Render() contracts share the same name

    output.Renderer returns (string,error) · nom.InlineRenderer returns nothing · nom.DependencyTree takes an arg

    renderer.go:6 nom/inline_renderer.go:104 nom/tree_render.go:16 
    Renderer.Render() (string, error)              // canonical — returns string + error
InlineRenderer.Render()                       // writes to io.Writer, returns nothing
DependencyTree.Render(maxHeight int) string  // takes a param, swallows errors into the string

    ⚠️ Why it's dangerous

    A reader seeing x.Render() cannot know the contract without checking the type. DependencyTree.Render silently encodes errors into its return string, which is the opposite philosophy from output.Renderer.

    ✅ How to fix

    • Rename InlineRenderer.Render() → Draw() or Flush() (it writes to a writer, not returns a string).
    • Rename DependencyTree.Render(maxHeight) → RenderString(maxHeight) or Format(maxHeight) to signal the different signature.
    • Reserve Render() (string, error) as the project-wide verb for the output.Renderer contract.
