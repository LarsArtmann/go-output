## Ideas Under Consideration

### Output Formats

| Idea                                  | What                                                                                                                                    | Why interesting                                                                                                                                                                                                                                                                                                                                  | Trigger to promote                                                                                                                                                                                                                                                 |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **CBOR** ([cbor.io](https://cbor.io)) | Concise Binary Object Representation (RFC 8949) — binary JSON-style serialization. Would live in `serialization/` alongside JSON/JSONL. | IETF standard for compact, schema-less binary encoding. Useful for IPC, persistence, and size/bandwidth-constrained contexts where text formats are wasteful. Symmetric with existing JSON/JSONL/TOML/YAML design — one new `Format` constant, one `init()` registration, one renderer. Candidate lib: `fxamacker/cbor` (well-audited, pure Go). | A real user surfaces a binary-output use case (e.g., embedding structured data in a binary protocol, MCU/edge targets, or inter-process pipes where JSON parse cost dominates). No action without concrete demand — 16 text formats already cover the CLI surface. |

### NOM Progress Visualization

| Idea                                | What                                                                                                                               | Why interesting                                                                                                                                                                                                                       | Trigger to promote                                                                                                                                                      |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Structured progress type**        | `ProgressDetail{Current, Total int; Label string}` replacing the free-form `ActivityProgress.Message string`                       | Current progress messages are unstructured text. A typed progress bar would enable rendering a visual `▓▓▓░░ 3/5` bar, percentage computation, and machine-readable progress for IPC. Deliberately deferred during BuildFlow integration. | A consumer (BuildFlow or external) needs machine-readable progress data, not just a display string.                                                                     |
| **Adaptive tree pruning**           | Nom-style "fill 1/3 of terminal, prune low-priority" algorithm. Current height-pressure collapse drops completed children but doesn't prioritize by critical path or recency. | Matches upstream nom's intelligent viewport management more closely. Would keep the most relevant activities visible without manual height tuning. Research-level — needs a priority model that handles real-world DAG shapes.        | A user reports that the tree is too tall or shows irrelevant activities under height pressure.                                                                          |
| **Live daghtml view**               | Wire `daghtml/` into `nom/` or `tui/` to render a live, auto-refreshing HTML DAG of the running workflow.                           | The daghtml SDK exists and renders interactive SVG DAGs, but it's only used for post-hoc visualization. A live view would be a differentiator vs upstream nom. Requires a file/socket-based refresh mechanism.                        | A user requests browser-based progress monitoring, or a CI integration that serves a live HTML dashboard.                                                              |
| **OSC 11 auto-theme query**         | Query terminal background color via OSC 11 escape sequence instead of relying on COLORFGBG env var alone.                          | More reliable than COLORFGBG (which many terminals don't set). Would improve `WithAutoTheme()` accuracy. Low-risk incremental improvement.                                                                                            | Users report auto-theme selecting the wrong preset on their terminal.                                                                                                   |
| **Tree-mode category collapse**     | Extend `WithCollapseCategories()` to tree mode (currently only works in layered mode).                                             | Groups sibling activities sharing a category into a summary line. Currently only in `RenderModeLayered`; tree mode users don't benefit. Moderate effort — needs tree-specific grouping logic.                                        | A user with many same-category activities in tree mode requests collapse.                                                                                               |
| **Explore `aymanbagabas/go-udiff`** | Replace the current `lastFrame` string comparison with a proper diff algorithm for frame updates.                                 | Could reduce bandwidth on large terminal updates by sending only changed lines instead of full frames. Research-level — current frame diffing works well enough for most cases.                                                       | Frame-update performance becomes a measurable problem on large trees (100+ activities).                                                                                  |

### Architecture

#### ~~Renderer Interface: `Render() (string, error)` — Code Smell~~

> **Resolved in v0.30.0.** The CQRS `WriteXxx(w io.Writer, model, opts...) error` (streaming, primary) and `RenderXxx(model, opts...) (string, error)` (convenience wrapper) pattern was implemented across all 16 formats. Registry dispatch now streams via CQRS functions. The original `Renderer` interface (`Render() (string, error)`) remains for backward compatibility but is no longer the primary API. See ADR 012.
